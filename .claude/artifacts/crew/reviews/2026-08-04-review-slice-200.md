# Review: SLICE-200 — unrecognized-verdict branch in review-gate.mts

## Task-scoped question 1 — is the vocabulary distinction real or post-hoc?

**Real.** Verified by tracing what writes/reads each field, not just reading
the comment:

- `REVIEW_SATISFIED`/`REVIEW_REJECTED` (review-gate.mts) classify the
  `decision` field of files under `.claude/artifacts/crew/reviews/`, read via
  `readNewestArtifactVerdict()` in `src/scripts/lib/artifact-verdict.mts:49`.
  That module's own header comment (line 4, predates this slice, written for
  dev-team P1.3) independently states the same split: *"reviews use {approved,
  approved_with_notes, rejected}; validations use {pass, fail, skipped}"* —
  this slice didn't invent the distinction, it documented one that was already
  architecturally load-bearing.
- `PASS_VERDICTS` (failure-classifier.mts:74) classifies the `verdict` field
  of `grades/*.md`, read via `grade.frontmatter?.verdict` in
  `collectGradeSignals()` (failure-classifier.mts:193). Entirely different
  artifact type, different directory, different writer (grade-writer, not
  reviewer).

These are two fields on two different artifact kinds that happen to share a
similar accepted-value shape. Merging the sets would require either (a)
changing what reviewers are allowed to write (out of scope, and AC-1's own
example depends on `PASS` staying unrecognized), or (b) changing what grade
writers emit (unrelated system, no defect reported against it). Declining to
merge is correct, not a rationalization.

## Task-scoped question 2 — the export

**Confirmed: zero production callers.** `grep -rn "REVIEW_SATISFIED\|REVIEW_REJECTED" src/` matches exactly three files: `review-gate.mts` (definition), and the new test file. No script, CLI, or agent prompt imports either set today.

Calling this out directly since it was asked for plainly: **this is FEAT-281's "tested-but-never-wired" pattern.** The export exists, a test imports and asserts on it (AC-2's test at line 106 of the new test file), and that combination reads as a delivered capability. At runtime nothing consumes it — the values are inlined identically in the `.reason` string generation regardless of whether the sets are exported or module-private. The "future code can import the canonical vocabulary" justification is speculative generality with no scheduled consumer in this slice, FEAT-283, or its sibling SLICE-201/202 scope (checked the FEAT-283 file's remaining defects — sort order and grandfather cutoff, neither needs this export).

This does not make the change wrong — `export` vs. no `export` is a one-keyword difference with no risk — but it should not be described as satisfying AC-2 via "documented intentional divergence" *and* "exported for future use" as if the export were load-bearing evidence of the reconciliation. The reconciliation is fully satisfied by the comment alone; the export is inert until something calls it. Recommend: either file a one-line follow-up noting this as a candidate for the next FEAT-281 sweep, or drop `export` now since nothing needs it yet (repo convention elsewhere favors module-private constants until a second consumer exists — e.g. `PASS_VERDICTS` itself is not exported). Not blocking.
