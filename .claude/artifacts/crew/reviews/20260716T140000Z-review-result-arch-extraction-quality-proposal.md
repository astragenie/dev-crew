## Summary

The chaff diagnosis is sound and the evidence is real (session-digest audit, quantified classes). The direction — declare validity horizon at write time, concentrate durable signal in a structured section, mark ephemeral orders — is worth pursuing. But the plan as scoped has one boundary error that makes T2 undeliverable as written, one coverage gap in the upstream ask that reproduces the exact failure mode the plan itself is trying to avoid, a success metric that no tooling in this repo can measure and that is silently gated on unscheduled upstream work, and an unaddressed duplication path onto a consolidation queue that is already documented as broken. None of these kill the direction; all of them should be resolved before a T-slice is dispatched to a builder.

## Findings

**[HIGH] T2 targets an artifact this repo (or dev-team) does not own.** T2 says "Owner: runner `agents/*.md` templates + workflow handoff format; dev-team mirror via upstream request." I grepped `agents/*.md` in this repo for `handoff` (case-insensitive) — zero matches outside one 3rdparty vendored agent. The "Handoff Format" contract (`objective / owner / allowed scope / forbidden scope / deliverable / changed files or evidence / confidence level / risks or open questions / suggested next handoff`) is defined exactly once, in `~/.claude/crew/workflow.md` — the **user's personal global config**, loaded into every repo's CLAUDE.md via `@~/.claude/crew/workflow.md`, not checked into either `runner-plugin` or (presumably) `dev-team`'s git tree. Neither plugin has a repo-owned handoff-format file to edit, and no CI gate in this repo validates handoff structure today. So T2 as scoped either (a) requires editing the user's out-of-repo personal file — a scope-creep this constitution itself would flag ("keep task scope explicit"), or (b) can only add prose to `agents/*.md` describing a convention that nothing reads or enforces, which is a materially different (and weaker) deliverable than what T2 currently promises. This needs to be resolved explicitly — pick one and say so — before dispatch; right now the plan is written as if a mirrored, dual-plugin, editable template exists, and it doesn't.

**[HIGH] The upstream E2 type-priors table has a coverage gap that reproduces the plan's own motivating failure mode.** E2: `todo`/`command`/`event` default session/task; `lesson`/`decision` default durable. There is no stated default for `fact` or `note` — yet the plan's own evidence table lists a durable "wire field names" **fact**, and issue #371 (which this proposal explicitly generalizes) gives two of its four noise exemplars as a **fact** (query-echo: "The recall_memory query used the search string...") and a **note** (near-identical date rephrase). An unaddressed default for these two types means one of two bad outcomes ships silently: either `fact`/`note` default to durable (in which case E1–E5 does nothing to the #371 exemplars it's supposed to generalize from — the proposal doesn't fix its own worked example), or they default to session/task (in which case durable contract facts like wire-field names get horizon-suppressed out of `agent_profile` — precisely the "silent knowledge loss, worse than chaff" risk the review brief called out by name). This is not a nuance to leave implicit; the upstream ask (issue #374) should state the `fact`/`note` default explicitly, not let it fall out of an incomplete table.

**[HIGH] Success metric has no measurement path today and is silently gated on unscheduled upstream work.** "Chaff <25% in a week" and "`agent_profile` top_lessons free of run-state atoms" require horizon labels per atom — that's entirely E1–E3 (upstream, astramem-local#374: filed same day as this plan, zero comments, no milestone, no assignee, no committed timeline). I grepped this repo's `src/` for `chaff`, `horizon`, `session_digest` — zero hits; there is no in-repo tooling to classify or count atom horizons. The only existing measurement method is the manual session-digest read that produced this plan's own evidence table. So "measure: rerun the session-digest audit after a week" (Sequencing step 4) is re-running the same manual, one-person, one-session audit — it is not a repeatable metric, and it cannot actually isolate the T-workstream's effect: T1–T4 add a marker and reorganize prose for humans; they do not relabel any atom or change what the extractor stores until E1–E3 land, which have no committed date. State the metric as "directional, manually re-audited, contingent on upstream E-work with no ETA" rather than a numeric target — as written it reads like a committed, measurable acceptance signal that the plan cannot actually deliver on its own.

**[MEDIUM] T1 marker is inert until E3 lands, and E3 has no timeline — the plan should say so, not imply an immediate effect.** T1's own text acknowledges this ("until then the marker alone makes prompt-echo trivially filterable" — filterable by a human, not by the extractor), but the plan's framing elsewhere (chaff-reduction sequencing, the metric) reads as though shipping T1 moves the needle before E3 ships. Given E3 is proposal-only with no committed date, the honest framing is: T1 ships a convention with zero measurable effect on the chaff numbers until an unscheduled upstream change lands. Worth stating as an explicit dependency risk in the plan's own risk section, which currently has none for "what if E never lands."

**[MEDIUM] Partial marker coverage is asserted, not evidenced.** T1 covers templated dispatch prompts in `runner`/`dev-team commands/agents`. It explicitly will not cover: ad-hoc `Agent()` calls (the credit-loop companion plan states "5/5 of today's real dispatches had none" of any ceremony), third-party vendored agents (`agents/3rdparty/*`, exempt from this repo's own content-length gate on the theory that they're not authored here — the same "not ours to template" logic applies to marker adoption), and free-typed user prompts. The plan doesn't attempt to attribute what share of the measured 27% instruction-echo originated from templated-dispatch prompts vs. these uncovered paths, so "moves the ~27% number materially" is an assumption, not a conclusion the evidence supports. A one-line breakdown (even rough) of the audited session's 30 echoed-`todo` atoms by dispatch-path origin would tell you whether T1's ceiling is worth building for.

**[MEDIUM] Template bloat has almost no headroom and isn't budgeted.** `agents/pm.md` is already at 332 lines against an already-bumped per-file override of 335 (`AGENT_LINE_OVERRIDES` in `src/scripts/validate-content-length.mts`) — 3 lines of slack. T2+T3 propose adding a "Durable learnings (memory-worthy)" / "Run evidence (ephemeral)" split plus (via T1) a `<task-scoped>` wrapper to every owned agent's dispatch guidance. The plan doesn't check current line counts or flag that this will very likely force another per-file override bump on `pm.md` (already an exception once) and possibly others (`architect.md` 122, `hierarchical-dispatcher.md` 127, `market-researcher.md` 187 have more room, but the pattern of "every owned agent gains another prompt block" is exactly how `pm.md` got to 332 in the first place, per that file's own override comment). Not a blocker, but the plan should account for it rather than treat template edits as free.

**[MEDIUM — technical debt] T4's dual-path story creates guaranteed duplication onto an already-broken consolidation queue.** T4 frames explicit slice-close capture as primary and transcript distillation as a "safety net, not the firehose" — but the safety net fires over the *same* handoff prose the explicit channel already wrote (T2's new "Durable learnings" section is, by design, the concentrated version of exactly what slice-close's lessons/surprises capture already sends via `memory-sink`). Absent an explicit suppression rule (e.g., "extraction must skip content already inside a `Durable learnings` block because it was captured explicitly"), every durable atom captured through the primary channel is also a strong distillation candidate from the transcript, i.e., a near-duplicate is the *expected* outcome, not an edge case. The existing consolidation-proposal backlog (astramem-local#372: 768 pending, 100% merge-kind, no auto-resolve, no committed timeline) is already documented as broken at current volume. The plan should either propose the exemption explicitly or acknowledge it's accepting more load on a queue that's already failing to drain.

**[LOW] Internal inconsistency: "no runtime code" vs. "one validate check."** Sequencing step 2 says "T1+T2+T3 = one runner-plugin slice (template/markdown edits + one validate check that dispatch templates carry the marker). No ceremony changes, no runtime code." A new validator is runtime code (a new `.mts` script) and a new CI gate — this repo's own CLAUDE.md treats the CI gate list as a curated, numbered, deliberate surface (currently 15 entries, each independently justified). Minor wording fix, but worth being precise about, since "no runtime code" is doing work in the plan's risk framing (implying this is markdown-only, lower-risk change) when it isn't quite.

## Invariant compliance (companion plan's ceremony-neutral, fail-silent, optional-never-gated)

- Ceremony/ gate untouched: yes for T1/T3/T4. No new step, no new failure mode in the ceremony sense.
- **Tension, not violation:** T2's "REQUIRED final section... (empty allowed: 'none')" sits awkwardly next to the credit-loop plan's hard invariant #5 ("`memories_used: [ids]` is an **optional** field... never validated/gated... avoids turning memory into a gate by the back door"). "Required but unvalidated, with an escape hatch of writing the literal word 'none'" is functionally optional — but the plan should say that plainly rather than use "REQUIRED," which reads as a stronger commitment than what's actually enforced. Given no validator will exist to check for the section's presence (per the finding above, there is no artifact to validate against even if desired), "REQUIRED" is aspirational language on an unenforceable target. Reword to match the sibling plan's discipline: "expected, never gated."
- Fail-silent / no new blocking behavior: consistent with the non-goals section — no objection here.

## Revisions required before T-slice dispatch

1. Resolve T2's ownership problem: either scope it to prose-only guidance inside `agents/*.md` (with the understanding that no shared, validated, dual-plugin "handoff format" file currently exists to change), or explicitly propose forking a repo-local handoff-format doc out of the user's global `workflow.md` — and say which, since they're different-sized pieces of work with different scope-creep risk.
2. Add explicit `fact`/`note` horizon defaults to the E2 ask in astramem-local#374 (or a follow-up comment) before treating E1–E3 as sufficient to fix the #371 exemplars this plan cites as motivation.
3. Reframe the success metric: state plainly that it is manually re-audited (not tool-measured), and that the numeric target is contingent on upstream E-work with no committed timeline — don't present it as a measurable week-one acceptance signal.
4. Add a suppression/dedup rule for T4 (skip distillation over content already inside a "Durable learnings" block, or otherwise state the accepted duplication and its interaction with the already-overloaded #372 consolidation backlog).
5. Fix the "no runtime code" claim in Sequencing step 2 to acknowledge the new validator.
6. Optional but recommended: soften T2's "REQUIRED" language to match the credit-loop plan's "optional, never gated" posture, given no enforcement mechanism will exist either way.

None of these require redesign — they're scoping and wording fixes plus one upstream-ask amendment (#2) — but items 1–3 in particular mean the plan's current sequencing ("one runner-plugin slice, ship now") is premature until they're addressed.
