# Review: SLICE-192 — key `materializeProposedSlices` off `id_suffix` identity

## Summary

`materializeProposedSlices` used to decide what to create purely by
`Math.max(existingSlices.length, startIndex)` — a raw count, never an
identity check. A dropped ordinal (the live FEAT-259 repro: ordinal 1
silently skipped, ordinals 2-5 materialized) made a rerun re-create the
LAST proposed entry as a duplicate while the real gap stayed missing, and
published a redundant GitHub issue (#598). This commit adds a durable
`proposed_slice_id_suffix` frontmatter stamp on newly created slices, keys
materialization off per-entry identity resolved via that stamp (or, for
every slice materialized before this fix shipped — i.e. all current
production data — an exact-title fallback), and fixes the idempotent-rerun
report to key off the same identity instead of positional pairing.

## Verified claims

1. **Title-match fallback chain holds.** Confirmed `proposed-slices.mts`
   caps `title` at `MAX_TITLE_LEN = 100` and `slice-title.mts`'s
   `SLICE_TITLE_MAX = 120`. `buildSliceMarkdown` stores `clampSliceTitle(title)`
   as the frontmatter `title`; since 100 < 120, `clampSliceTitle` only
   `.trim()`s (no truncation), so for a title with no leading/trailing
   whitespace the stored value is byte-for-byte the proposed entry's title.
   Confirmed `matchProposedIdSuffix` compares against `sliceFrontmatter.title`
   (the frontmatter field), not the body-heading `safeTitle` derived
   separately — there's only one `title`, so no divergence there.

2. **Round-trip fidelity for special characters is safe.** Traced
   `serializeFrontmatter`/`parseFrontmatter` (`frontmatter.mts`) by hand for
   titles containing a colon, a quote, a leading `[`, and a `#`:
   `serializeScalar`'s `QUOTE_NEEDED_RE` (`[:#[\]{}'",]`) wraps any of these
   in a double-quoted scalar, escaping only embedded `"`; `stripQuotes` /
   `unescapeDoubleQuoted` reverse it exactly on parse. All four probe cases
   round-trip correctly, including inside `proposed_slices`' array-of-mappings
   serialization (`emitArrayOfMappings` calls the same `serializeScalar`).

3. **Single-slice path confirmed unaffected.** `materializeSingleSlice`
   (feature-lifecycle.mts:404-429) does not pass `proposedSliceIdSuffix` to
   `createSlice`, so the field is never stamped on that path. No slice
   frontmatter JSON schema exists in `schemas/` that constrains slice
   markdown fields (only `slice-event.schema.json`, an unrelated event
   shape), and `validate-manifests.mts` only checks commands/agents/skills
   frontmatter — neither is affected by the new key.

4. **Publish safety (AC-5) confirmed on the actual code path.** `loop.mts`
   `SLICE_HANDLERS["from-feature"]` (line 1567) iterates `out.slices` and
   calls `publishSliceViaProvider` for every entry unconditionally — it does
   **not** gate on `out.idempotent`, so this also runs on idempotent
   reruns. That looked risky in isolation, but `publishSlice`
   (`scripts/lib/github-sync.mjs:707`) is itself idempotent: it checks
   `sliceFm.github_issue` on the slice file and short-circuits with no `gh`
   calls if already published. So the idempotent branch returning
   already-materialized siblings in `out.slices` is safe (as it was before
   this commit — same shape existed pre-fix) precisely because the
   downstream publish call is a no-op for slices that already carry an
   issue stamp. The actual AC-5 guarantee this slice adds — the **create**
   path's returned array containing only genuinely-new slices, never an
   already-materialized sibling — is real and is what the third new test
   (`publish-safety`) exercises; confirmed by reading it, not just trusting
   the assertion names.

5. **`reconcileProposedSlicesStartIndex`'s `existingCount` residual —
   assessed, not a regression.** `existingCount =
   Math.min(existingSlicesRaw.length, proposed.length)` is still a raw
   count, blind to identity, exactly as `Math.max(existingSlices.length,
   startIndex)` was pre-fix. Worked through the disagreement cases by hand:
   when `existingCount` happens to diverge from the identity-resolved
   count, `planReconcileAction`'s `proceed` branch doesn't itself decide
   what to create — it just declines to force an `advance`, and the
   identity-based `toCreate` computation downstream still runs and fills
   the real gap correctly regardless of position. The one case that can
   still go wrong (git evidence marking an ordinal "shipped" that has no
   local file, causing `coveredByStartIndex` to suppress a genuine gap) is
   a pre-existing characteristic of the independent git-anchored-completion
   mechanism (`runner-plugin#392`/FEAT-284's git-reconcile pass), unchanged
   by this commit — the builder's comment correctly frames it as
   orthogonal/composable rather than hiding it. Confirmed: not a new hole
   introduced by SLICE-192, but agree with flagging it as a residual worth
   its own ticket if it isn't already tracked.

6. **AC-1 test asserts both halves.** Read
   `slice-from-feature-proposed-slices.test.mts`'s first new test in full:
   it asserts the created slice's title is ordinal 1's ("Fixture rebuild"),
   that the new id is not among the 4 legacy ids, that
   `frontmatter.slices.length === 5` after the fill, and that the resulting
   set equals `legacyIds ∪ {newId}` exactly (no loss, no dupe) — then reruns
   once more and asserts full idempotency. This is not a
   duplicates-only-absence check; it positively asserts the gap got filled.

## New findings (not blocking, recommend fast-follow)

**A. `proposed_slices` has no uniqueness validation — title or `id_suffix`
— in `proposed-slices.mts`'s `validateOne`/`parseProposedSlices`.** Two
consequences if a future PM decomposition ever authors a duplicate:

- **Duplicate `title` across two entries in one FEAT:** in
  `resolveMaterializedIdSuffixes`, `matchProposedIdSuffix`'s
  `proposed.find((p) => p.title === title)` returns the *first* matching
  entry for every legacy slice with that title. If two legacy slices
  (materialized for the two different, same-titled, proposed entries) both
  resolve to the same `id_suffix` via `.find()`, only the first slice
  claims that suffix in `bySuffix` (`!bySuffix.has(idSuffix)` guards the
  second write) — the *second* proposed entry then has no
  `materializedId`, appears "missing," and would be **created again**,
  producing a genuine duplicate slice for content that already exists on
  disk. This is the same failure class SLICE-192 exists to fix, just
  reached through a different door.
- **Duplicate `id_suffix`:** the inverse failure — both entries would
  resolve to the same slice, so the second is silently swallowed
  (never created), a quieter data-loss mode.
- Scanned the live backlog (`.claude/artifacts/loop/backlog/{done,
  in-progress,pending,triaged}/FEAT-*.md`) for duplicate `title`s within a
  single FEAT's `proposed_slices` — **none found today**, so this is not a
  live incident, only a latent design gap. Recommend adding a
  uniqueness check (on `id_suffix` at minimum, ideally also `title`) to
  `parseProposedSlices` as a fast-follow, since the identity-matching
  contract this slice just built implicitly assumes both are unique.

**B. `clampSliceTitle`'s `.trim()` can silently break the legacy-title
fallback for whitespace-padded titles.** `proposed-slices.mts`'s
`validateOne` only checks `title.length`, not a trimmed length, so a
proposed title with leading/trailing whitespace passes validation
unchanged. `buildSliceMarkdown` then stores `clampSliceTitle(title)`,
which `.trim()`s before the length check — so the *stored* frontmatter
title differs from the *proposed* entry's raw title by whitespace.
`matchProposedIdSuffix`'s `===` comparison is exact, so it would never
match. Per the builder's own doc comment this "degrades to unknown, not a
wrong answer" — but for the legacy-slice case specifically, "unknown"
means the entry shows up in `toCreate` on every single rerun (there's no
stamp to fall back to for a slice materialized under the fallback), i.e.
a padded title reintroduces an unbounded duplicate-creation loop rather
than gracefully degrading. Not exercised by the current backlog (no
whitespace-padded titles found in the scan above) and easy to close with a
one-line `.trim()` on both sides of the comparison (or at parse time in
`proposed-slices.mts`) as a fast-follow.

Neither finding blocks this slice — both are pre-existing gaps in
`proposed_slices` authoring validation that this fix's identity contract
newly depends on, not something the diff itself got wrong, and neither
reproduces in current production data.

## Decision: approved_with_notes

The fix correctly replaces count-based materialization with
identity-based resolution, is covered by tests that assert the actual gap
gets filled (not just duplicate-absence), doesn't regress the single-slice
path or any schema/consumer, and closes the real AC-5 publish-safety hole
on the create path. All CI gates pass; the one test failure in the full
run is pre-flagged known-flaky and unrelated to the changed files. File
findings A and B as fast-follow tickets before the next PM decomposition
cycle broadens `proposed_slices` authoring.
