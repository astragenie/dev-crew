# Review — SLICE-155 (FEAT-251 Phase 2, tracker-provider migration)

## Verdict: PASS

No MAJOR or blocking findings. Two MINOR/informational notes below. All 5 ACs verified against the actual diff (not just the builder's self-report), tests and typecheck re-run independently and confirmed green.

## What I checked and confirmed

1. **Zero remaining direct github-sync calls in loop.mts** — confirmed independently via `grep -n "importGithubSync\b" src/scripts/loop.mts` (0 matches), not just the AC-4 grep test. The `./lib/github-sync-loader.mjs` import is gone.

2. **Parity of the 5 new GithubProvider id-based methods** — read `scripts/lib/github-sync.mjs`'s actual exports (`publishFeat`, `publishSlice`, `publishAll`, `syncMilestones`, `setupGithubSync`) and confirmed each new provider method (`publishFeatureById`, `publishSliceById`, `publishAll`, `syncMilestones`, `setup`) calls the identical function with the identical argument shape (`{ ghExec, config }` options object), not a reimplementation. Idempotency checks, milestone upserts, and frontmatter stamping all still live in github-sync.mjs and are reached unchanged.

3. **Never-throw / warn-and-continue contract** — verified for all four migrated flows. The three auto-publish sites (backlog-add, spec-decompose, slice-from-feature) keep their original try/catch wrapping `publishFeatureViaProvider`/`publishSliceViaProvider`; a non-GithubProvider resolution returns `null` without throwing (matches the pre-refactor `isEnabled()===false → return null` path byte-for-byte). The `github`/`task-store` subcommand family returns fixed no-op shapes (`{skipped:true}`, `{milestones:0,...}`) rather than throwing. AC-3 tests assert `doesNotReject` for all of these — confirmed the tests actually exercise a fully-unconfigured `config = {}` repo, not a trivially-true case.

4. **Windows `pathToFileURL` fix** — real and correct. `importGithubSyncModule` previously handed a raw OS path string to dynamic `import()`, which Windows parses as a bare specifier (not a filesystem path) and fails; `pathToFileURL(modulePath).href` is the standard, platform-correct fix and works identically on POSIX. The new third candidate path (`.../scripts/lib/github-sync.mjs`, a *sibling* of the `github-sync/` submodule folder) is verified correct — I confirmed the file actually lives at `scripts/lib/github-sync.mjs` relative to repo root, matching the 5-levels-up-then-`scripts/lib` resolution from `src/scripts/lib/task-store/providers/`. The claimed pre-existing masking is also verified: `src/tests/task-store-github-provider.test.mts`'s syncPull/bootstrap tests only ever inject a *throwing* `ghExec` (simulating "gh not installed"), which short-circuits at `_isInstalled()` before ever reaching the broken import — so this bug really was latent and untested before this slice. The new routing tests (AC-1/AC-5) use a working `mockGhExec` and hit `importGithubSyncModule("github-sync.mjs")` for real via the *same shared helper function* also used by `syncPull`/`bootstrap`, so the fix's applicability to those two methods is a sound inference even though no test drives them end-to-end with a working exec.

5/6. **Double-gate fix / config-matrix impact** — walked the full matrix (`github.enabled` ∈ {true, false, absent} × `taskStore.provider` ∈ {github, noop, absent}) against `getProvider()`'s actual resolution order in `src/scripts/lib/task-store/index.mts`:
   - `taskStore.provider: "github"` (explicit) → always resolves `GithubProvider` regardless of `github.enabled`. Pre-refactor, this case only *actually* published when `github.enabled: true` was also set (isEnabled() gate inside github-sync.mjs). Post-refactor, `_enabledConfig()` forces `enabled: true`, so it now publishes even without `github.enabled: true`. **This is the disclosed, intentional AC-5 fix** — directly required by FEAT-251's explicit AC-5 text and its "single switch for ALL mirror traffic" framing.
   - `taskStore.provider: "noop"` → always resolves `NoopProvider` regardless of `github.enabled`. Pre-refactor, the three auto-publish sites and the `publish`/`status`/`feat-publish` subcommands ignored `taskStore.provider` entirely and published whenever `github.enabled: true`, so `noop` + `github.enabled:true` used to still publish. Post-refactor it now no-ops everywhere. **This is exactly the risk the builder's handoff flagged**, and it matches FEAT-251's stated intent that `taskStore.provider` become the single switch.
   - `taskStore.provider` absent, driven purely by `github.enabled` → unchanged in both directions (true → publish, false/absent → no-op) — no behavior change.
   - I found one additional matrix cell not explicitly named in the builder's risk note but in the same category: `taskStore.enabled: false` (the top-of-function override in `getProvider`) combined with `github.enabled: true` also now no-ops where it previously would have published, for the same "getProvider is now authoritative" reason. Not a new class of risk — same direction and same design intent as the disclosed noop case — but worth naming explicitly for the record. **Not a MAJOR finding**; no undisclosed cell silently changes in a way inconsistent with the FEAT's stated intent.
   - **Visibility of the no-op**: `runGithubFeatPublish` and the pre-existing pre-refactor code both log `"[github-sync] GitHub sync disabled — skipped."` on skip — that one is visible. However, `publishFeatureViaProvider`/`publishSliceViaProvider` (the three auto-publish call sites) and `runGithubPublish`/`runGithubStatus` no-op completely silently (no console output at all beyond the CLI's generic JSON-result echo for the subcommand path). This exactly matches the pre-existing silent-null behavior of `isEnabled()===false`, so it is **not a regression**, just not the enhanced visibility the review brief hoped to find. MINOR, non-blocking.

7. **`runGithubSubcommand` split** — traced each of the 5 extracted handlers against the original inline logic: argument parsing (`flags?.id || positionals[1]` for feat-publish), the `"github requires a subcommand..."` error text, the `setup` special case (never gated on config before or after — pre-refactor `setup` didn't even resolve config; post-refactor `runGithubSetup` also doesn't consult `getProvider()`, by design, since setup bootstraps `github.enabled` itself), and output shapes (`{created, issueNum, url}`, `{milestones, issues, subissues}`, `{milestones, updated, closed}`) all preserved exactly.
