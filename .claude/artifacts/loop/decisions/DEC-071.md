# DEC-071: one documented cap policy for memory capture and recall

## Context

The v0.64.0 architect design review (FEAT-233 triage) flagged that the memory
transport's wallclock caps never had a deliberate, single policy:

- Capture (`memory-sink.mts::recordMemory`) hardcoded `CAP_MS = 2000` as a
  bare module constant.
- Recall (`slice-linker/start-slice.mts::runRecallHook`) read
  `config?.memory?.recall?.timeoutMs ?? 5000` — a separate hardcoded literal.

Neither site referenced the other. The 2000/5000 split was incidental to how
each path was built (capture landed first under FEAT-217; recall's
config-driven override landed later under FEAT-188 S3b), not a decision
anyone made about how long capture vs. recall should be allowed to run.

## Decision: shared default constant + documented per-path override. Accepted.

`memory-transport.mts` becomes the single source of truth for both defaults:

- `DEFAULT_MEMORY_CAP_MS = 2000` — the shared baseline default, read by
  capture.
- `DEFAULT_RECALL_CAP_MS = 5000` — recall's own default, a documented
  override of the shared baseline (rationale below), not a second
  independent magic number.

Both paths now resolve their cap through the same three-tier chain, reading
from the same `memory` config block:

- **Capture** (`memory-sink.mts::recordMemory`): `memory.capMs` (new,
  optional config override) else `DEFAULT_MEMORY_CAP_MS`.
- **Recall** (`start-slice.mts::runRecallHook`): `memory.recall.timeoutMs`
  (existing, unchanged key — recall's own explicit override) else the same
  `memory.capMs` else `DEFAULT_RECALL_CAP_MS`.

### Why recall gets a longer default than capture

Recall runs once per slice-start, not on a hot per-call path the way capture
runs (every decision/lesson/note/failure record). It also feeds directly into
the quality of the builder's dispatch context — a slow-but-reachable astramem
backend is worth waiting a little longer for before falling back to an empty
recall block. Capture is fire-and-forget bookkeeping that must never make a
close/learn/decision path feel slow, so it keeps the tighter 2s default.

This is the documented rationale AC-3 requires: the asymmetry is now a named
policy (recall intentionally allows a longer cap) instead of two unrelated
literals that happened to differ.

## Consequences

- No behavior regression for unconfigured repos: with no `memory.capMs` and
  no `memory.recall.timeoutMs` set, capture still caps at 2000ms and recall
  still caps at 5000ms — byte-identical to pre-DEC-071 behavior.
- A repo MAY now set one `memory.capMs` to raise (or lower) both paths'
  budgets together, or set `memory.recall.timeoutMs` alone to diverge recall
  from capture without touching the shared knob.
- Neither cap was removed or weakened — this DEC only unifies *where the
  numbers come from*, per the FEAT-233 constraint to never regress the
  existing caps' safety.
- Cancellation (making the losing call ACTUALLY stop running past the cap,
  not just abandoning it) is a separate, upstream-blocked concern — see
  `docs/upstream-requests/2026-07-08-astramem-plugin-abortsignal-cancellation.md`
  and the KNOWN LIMIT note on `memory-transport.mts::sendViaProvider`. This
  DEC covers policy reconciliation (AC-3) only, not AC-1/AC-2.
