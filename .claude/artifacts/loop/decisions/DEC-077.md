# DEC-077: Reconcile FEAT-102 (Linear teammate flow) as superseded by FEAT-252; delete the unwired scripts/linear-sync/ webhook prototype

## Context

FEAT-102 ("Linear teammate flow (assign-to-Crew)") was marked `status: done`
on 2026-06-13, but its acceptance criteria were never fully satisfied:

- `LinearProvider` was never upgraded past the FEAT-024 stub (all methods
  throw).
- The webhook receiver AC (`scripts/linear-sync/webhook.mjs`) was partially
  built as `scripts/linear-sync/webhook-handler.mts` (different filename,
  same intent) but was never wired to any live endpoint or dispatch path.
- The round-trip AC (Linear issue → FEAT/SPEC → PR; PR closes → Linear
  status → Done with grade summary in comment) was never implemented or
  demonstrated.
- The mention-parser and reply-formatter snapshot tests exist
  (`scripts/linear-sync/*.mts`, unit-tested) but the docs AC
  (`docs/integrations/linear-teammate.md`) was never written.

This FEAT-256 hygiene task (Phase 0 of the tracker-provider migration
program, `.claude/artifacts/crew/runs/2026-07-09-tracker-provider-migration-prompt.md`)
requires reconciling this done-but-unsatisfied FEAT and deciding the fate
of the orphaned `scripts/linear-sync/` prototype before Phase 3
(`FEAT-252`, real `LinearProvider` implementation) starts.

## Decision

### Part A — FEAT-102 reconciliation

FEAT-102 is formally **superseded by FEAT-252** (LinearProvider — Phase 3
of the tracker-provider migration program, and the same work item as the
Watcher-track plan's C2 slot deferred by FEAT-245/IssueBroker) **and
FEAT-254** (issue-flow hooks — Phase 5: close-comment + issue-close via
provider, `intake --from-issue` Linear URLs, `issue.published`/
`issue.closed` emitters — which delivers the outbound half of FEAT-102's
round-trip ambition). FEAT-102's
frontmatter `status: done` is left unchanged — flipping it back to
`in-progress`/`pending` would misrepresent history (real work did land:
the mention-parser and comment-router prototype) and would fight the
backlog state machine for no operational benefit. Instead, FEAT-102's
body gains a `## Reconciliation (DEC-077)` section (see
`.claude/artifacts/loop/backlog/done/FEAT-102.md`) recording the
unsatisfied AC and the superseded-by pointer, so anyone reading FEAT-102
in `done/` sees the caveat without a frontmatter mutation.

FEAT-102's full original scope — a Linear **teammate flow** (watch
issue-assignment to a "Crew bot" user, `@crew` mention commands, webhook
receiver, round-trip status sync) — is **broader** than FEAT-252's scope
(FEAT-252 is the outbound `LinearProvider`: `issueCreate`,
`issueCreate+parentId`, workflow-state transitions, `commentCreate`
against the Linear GraphQL API; see Phase 3 in the migration prompt).
FEAT-102's inbound/webhook/mention-driven half is explicitly deferred
further out — to the Watcher track (FEAT-245 IssueBroker / C1, which
already documents "LinearProvider slot deferred to C2") and is NOT
picked back up by FEAT-256 or FEAT-252. If the teammate-flow AC is
wanted again, it needs its own future FEAT built on top of a working
`LinearProvider`, not a resurrection of FEAT-102 itself.

### Part B — fate of scripts/linear-sync/

**Delete** (not fold), execution deferred to FEAT-252 SLICE-1 per the
dispatch contract for this slice (SLICE-154 is markdown-only; no source
deletion happens here).

Rationale, from reading the three files
(`linear-types.mts`, `mention-parser.mts`, `webhook-handler.mts`):

- `linear-types.mts` defines **inbound webhook payload shapes**
  (`LinearWebhookPayload`, `LinearIssueData`, `LinearCommentData`) and
  mention-command types (`CrewCommand`, `CrewMention`). FEAT-252 needs
  **outbound GraphQL mutation/response types** for `issueCreate`,
  `commentCreate`, and workflow-state transitions against
  `https://api.linear.app/graphql` — a structurally different problem
  (request input types + typed response payloads, not webhook event
  shapes). None of the fields here are reusable as-is for that surface.
- `mention-parser.mts` is a regex (`@crew\s+(triage|build|status)`)
  over inbound comment bodies — this is teammate-flow logic (Part A),
  not LinearProvider logic. FEAT-252 never parses inbound Linear text.
- `webhook-handler.mts` routes inbound webhook payloads to
  `CrewMention` actions — same inbound-only concern, no outbound API
  client, no auth handling, no id-mapping logic that FEAT-252 could
  start from.
- All three files are `// @ts-nocheck`'d and outside `tsconfig`
  `rootDir`, unit-tested but wired to zero call sites (`grep -rn
  "linear-sync" src/ scripts/ commands/ agents/` — no imports outside
  the directory itself; correction, review 2026-07-10: one import DOES
  exist — `src/tests/linear-webhook.test.mts` imports all three files.
  Test-only consumer; it must be dropped in the same FEAT-252 SLICE-1
  deletion step as the directory itself). Carrying zero-consumer, type-checking-exempt
  code across three more phases of this program is drift risk with no
  offsetting reuse value once Part A's conclusion (webhook/teammate
  flow is out of scope for this program) is taken into account.

If a future FEAT resurrects the teammate-flow AC (webhook receiver +
mention parsing + round-trip), the tested logic here is fully
recoverable from git history (this commit, and FEAT-102's original
landing commit) — deleting now does not destroy the design, it removes
dead weight from the active tree.

**Instruction to FEAT-252's builder (SLICE-1):** run
`git rm -r scripts/linear-sync/` (and drop any now-empty test files under
`src/tests/` that only covered this directory) as the first mechanical
step of SLICE-1, before writing the real `LinearProvider` GraphQL client.
Do not attempt to adapt `linear-types.mts` — write fresh GraphQL
input/response types scoped to the mutations Phase 3 actually calls.

## Consequences

### Positive

- FEAT-102 stays historically accurate (real prototype work is
  acknowledged) while the backlog no longer silently implies the Linear
  teammate flow shipped.
- FEAT-252 starts from a clean slate for its GraphQL client instead of
  bending an inbound-webhook-shaped prototype to fit an outbound-API
  problem.
- Dead, `@ts-nocheck`-exempt, zero-consumer code is scheduled for
  removal on a concrete trigger (FEAT-252 SLICE-1) rather than lingering
  indefinitely.

### Negative

- The mention-parser and webhook-router logic (recoverable from git
  history) will need to be rewritten, not just re-wired, whenever the
  teammate-flow AC is picked back up — there is no living code to build
  on directly once deleted.
- FEAT-252's SLICE-1 scope grows by one small mechanical step (the
  `git rm`), which must be remembered at that slice's start since this
  DEC is the only record of the instruction.

### Neutral

- No frontmatter changes to FEAT-102 — its `done` status, dates, and
  other fields are untouched; only a body section is appended.

## Alternatives considered

- **Option A — supersede FEAT-102, delete scripts/linear-sync/ deferred
  to FEAT-252 SLICE-1 (chosen).** Keeps this slice markdown-only (per
  its dispatch contract), records the deletion as a concrete future
  task instead of leaving the fate ambiguous, and matches the actual
  code-reuse analysis (no outbound-API reuse value).
- **Option B — fold mention-parser + linear-types into FEAT-252.**
  Rejected: the prototype's types and parser are inbound/webhook-shaped;
  FEAT-252 is an outbound GraphQL client. Folding them in would mean
  carrying unused types and an unused regex parser into the new
  provider module, which is worse for maintainability than writing the
  small amount of genuinely-new GraphQL types FEAT-252 needs.
- **Option C — reopen FEAT-102 to `in-progress` and let FEAT-252 finish
  it under the original id.** Rejected: FEAT-252 is scoped narrower
  (outbound provider only) than FEAT-102's full teammate-flow AC;
  reopening FEAT-102 would either require re-scoping it down (confusing
  history) or leaving it open against work FEAT-252 was never going to
  finish (webhook receiver, mention commands, round-trip), which is the
  same "done but actually not" problem this DEC exists to fix.
- **Option D — delete scripts/linear-sync/ immediately in this slice.**
  Rejected by the slice's own dispatch contract (SLICE-154/FEAT-256 is
  markdown-only hygiene, no source-code edits); also useful to keep the
  deletion co-located with FEAT-252's SLICE-1 work so it lands in the
  same review pass as the code that supersedes it, rather than as an
  unrelated deletion commit with no immediate replacement.
