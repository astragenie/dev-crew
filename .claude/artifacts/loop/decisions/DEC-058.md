# DEC-058: PM triage-score persistence is a hybrid — PM writes a reviews file, a new pm-apply CLI subcommand validates and commits frontmatter

## Context

FEAT-214 surfaced a live break in the intake/triage write path:
`skills/triage/SKILL.md` step 7 still instructs
`bun loop.mts backlog pm-write --id ... --scores '{...}' ...`, but that
subcommand was deleted in v0.53 (FEAT-277) — `src/scripts/loop.mts:951`
now carries only the comment `// runBacklogPmWrite removed in v0.53 —
backlog-pm-write.mts deleted (FEAT-277)`. No replacement writer was
shipped. `agents/pm.md` frontmatter grants `Edit, Write` (line 8), but
its own "Boundaries" section (line 207) states "Read-only. Never Edit,
Write, or move backlog files" — an unauthorized-by-prose gap between
grant and behavior. The result: triage scores have no owner, and the
FEAT-214 live run required an operator to hand-drive
`backlog-writer.mts` library functions to complete the write.

Three write-ownership options were evaluated:

- **(A) Restore a `pm-write`-equivalent CLI subcommand.** Orchestrator
  (the `skills/triage/SKILL.md` slash flow) drives it directly, as
  before v0.53. PM stays read-only.
- **(B) Authorize PM agent self-writes.** Update `agents/pm.md`
  Boundaries prose to match its existing `Edit, Write` tool grants; PM
  writes backlog frontmatter directly.
- **(C) Hybrid.** PM writes a structured results file to
  `.claude/artifacts/loop/pm-reviews/` (using its existing `Write`
  grant, scoped to a review-artifact directory, never backlog files).
  A new CLI subcommand `pm-apply` reads that file, validates it against
  the FEAT schema, and commits the frontmatter update atomically via
  the existing `updateFeatureFrontmatter` / `moveFeature` library
  functions in `src/scripts/lib/backlog-writer.mts`.

Constraints considered:

- **DEC-011 precedent** ("CLI auto-dispatch removed; slash flows are
  the contract"): CLI subcommands that mutate backlog state must be
  invoked by a slash flow, not by an agent spawning another agent or
  writing state on its own initiative. DEC-011 did not forbid CLI
  subcommands that *perform* a validated write when called by an
  orchestrating slash flow — it forbade `dispatchAgent` marker-write
  indirection with no consumer. The pre-v0.53 `pm-write` subcommand
  was exactly this: a slash-flow-invoked, schema-validated CLI write.
- **FEAT-213** (triaged, P1, security): explicitly asks for PM's tool
  grants to be *reconciled down* — either drop `Edit`/`Write` from
  `agents/pm.md` frontmatter, or document the specific narrow case
  where PM legitimately writes. FEAT-213 AC-1 treats an unexplained
  gap between grant and boundary as the defect to close, and its
  broader problem statement is injection blast-radius: PM reads
  untrusted FEAT bodies and its output feeds unattended builder
  dispatch under `marathonMode`.
- **Windows mtime/cache quirks**: `backlog-writer.mts:157-161`
  documents that Windows mtime granularity (~16ms) can let rapid
  writes share an mtime with prior content, pinning
  `readFrontmatterCached` to a stale parse unless
  `clearFrontmatterCache()` runs after the write. This workaround
  lives inside `updateFeatureFrontmatter` — any write path that
  bypasses that function reintroduces the stale-read bug class on this
  Windows host.
- **Auditability**: FEAT-214 AC-5 already requires PM to persist
  per-FEAT results to `.claude/artifacts/loop/pm-reviews/` as scoring
  completes, specifically so a truncated 11+-FEAT batch's final
  message doesn't lose already-scored results. This artifact is a
  prerequisite for durability regardless of which write-ownership
  option is chosen.
- **Testability**: PM's JSON output is currently transported as
  `--scores '{...}'` CLI argv — a string that must survive PowerShell
  and bash quoting on this win32 host, a known source of escaping
  bugs. A file-based hand-off sidesteps argv quoting entirely and is
  independently unit-testable with a fixture file, without invoking
  the LLM agent.

## Decision

We will adopt **(C) hybrid**: PM persists scoring results to a
structured file under `.claude/artifacts/loop/pm-reviews/` (already
required by FEAT-214 AC-5) using its existing `Write` grant, scoped
narrowly to that review-artifact directory. A new CLI subcommand,
`bun loop.mts backlog pm-apply --review <path-or-id>`, reads that file,
validates it (schema + the AC-2 field-name reconciliation between
`agents/pm.md`'s `featureId`/`demandEvidence` and whatever field names
the review file uses), and commits the frontmatter update atomically
via the existing `updateFeatureFrontmatter` / `moveFeature` functions
in `backlog-writer.mts` — inheriting the Windows mtime/cache-bust fix
for free. `skills/triage/SKILL.md` step 7 is rewritten to call
`pm-apply` instead of the deleted `pm-write`, preserving DEC-011's
"slash flow drives the CLI write" shape. `agents/pm.md`'s Boundaries
section is corrected to name the one legitimate write case (the
reviews-file artifact) rather than leaving the blanket "never Edit,
Write" claim standing against a broader `Edit, Write` grant — this is
the FEAT-213 AC-1 reconciliation, resolved by narrowing rather than
by broadening prose to match the existing grant.

## Consequences

### Positive

- PM's write footprint stays narrow and auditable: it can only ever
  write review artifacts, never backlog frontmatter directly — the
  injection blast radius FEAT-213 is concerned with (an engineered
  FEAT body inducing a bad write) is capped at a discardable review
  file, not a corrupted backlog state transition.
- Backlog frontmatter mutation stays inside one already-tested,
  Windows-mtime-safe code path (`updateFeatureFrontmatter` /
  `moveFeature`), instead of a second ad hoc write path that would
  need to reimplement the same cache-invalidation fix.
- Solves FEAT-214 AC-5 (batch-truncation durability) and the
  write-ownership question with one artifact shape — no separate
  "durability" and "who writes" mechanisms to keep in sync.
- `pm-apply` is unit-testable against a fixture reviews file without
  dispatching the LLM agent, and side-steps PowerShell/bash argv
  quoting entirely (no more `--scores '{...}'` JSON-in-a-flag).
- Consistent with DEC-011: the slash flow (`skills/triage/SKILL.md`)
  remains the orchestration contract; `pm-apply` is a plain
  validated-write CLI subcommand it calls, not agent-to-agent
  auto-dispatch.

### Negative

- Two-step write (PM writes reviews file, then `pm-apply` commits
  frontmatter) is one more moving part than a single `pm-write` call —
  a review file could exist on disk with no corresponding `pm-apply`
  run if the slash flow halts between steps. Mitigated by making step
  7's `pm-apply` call idempotent and re-runnable from the reviews
  directory (an operator can re-run it standalone after a halt).
- Requires both a new library function (or extension of
  `backlog-writer.mts`) for `pm-apply` and a schema for the reviews
  file — more surface than resurrecting the old `pm-write` verbatim.

### Neutral

- `agents/pm.md`'s tool grant list still nominally includes `Write`
  (needed for the reviews-file case) — FEAT-213's reconciliation is
  satisfied by narrowing the *documented* boundary to that one case,
  not by dropping the grant, since PM legitimately needs `Write` for
  the reviews artifact.

## Alternatives considered

- **(A) Restore a `pm-write`-equivalent CLI subcommand, orchestrator
  drives it directly.** Cleanly matches DEC-011's "slash flow calls a
  validated CLI write" shape and keeps PM fully read-only, which is
  the simplest read against FEAT-213. *Why rejected*: does not solve
  FEAT-214 AC-5's batch-truncation durability requirement (PM's final
  message is still the sole results transport, and an 11+-FEAT batch
  can truncate before the orchestrator ever sees the JSON to pass to
  `--scores`), and keeps the fragile `--scores '{...}'` JSON-in-argv
  transport that is a known Windows quoting hazard. A results file was
  going to be required regardless, so option A would only be step one
  of option C without the atomic-validation layer.
- **(B) Authorize PM agent self-writes; update Boundaries prose to
  match its `Edit, Write` grants.** Simplest code change (prose-only)
  and removes the CLI round-trip entirely. *Why rejected*: directly
  conflicts with FEAT-213, which asks for PM's write footprint to be
  minimized, not formalized and widened to cover every backlog
  frontmatter file. Self-writes from an agent that reads untrusted
  FEAT bodies (github-sync ingestion path) mean a successful prompt
  injection can mutate `pm_*` scores, `status`, or move files between
  `pending/`/`triaged/` directly — no schema gate, no CLI-level audit
  point, and no reuse of `updateFeatureFrontmatter`'s Windows
  mtime/cache-bust fix unless PM's own Write calls happen to route
  through that exact function (unenforceable from a prompt).
- **(C) Hybrid — PM writes reviews file; `pm-apply` validates and
  commits.** Selected. See Decision above.
