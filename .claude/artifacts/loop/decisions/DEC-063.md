# DEC-063: Snapshot freshness gate excludes the volatile Dispatch lifecycle section

## Context

Merging `feat/envelope-v1.1-enrichment` onto `main` brought FEAT-205
(the `## Dispatch lifecycle` section in `loop-snapshot.md`, rendered from
live dispatch state — open-run count, worktree count, oldest-run age in
days) together with FEAT-208 (the CI snapshot-freshness gate, which
regenerates the snapshot in-memory and requires byte-for-byte equality
with the on-disk file). FEAT-208's contract assumes the snapshot is "pure
aggregation" and therefore reproducible. FEAT-205's section is not:
`worktreeCount` reflects live `git worktree` state (a clean CI checkout
has zero) and `oldestRunAgeDays` grows every hour. The two features are
individually correct but mutually incompatible under strict equality — CI
failed on the first merge that combined them.

## Decision

The freshness gate excludes the `## Dispatch lifecycle` section from the
diff. `validateSnapshotFreshness` strips that section (header through the
line before the next `## ` heading) from both the on-disk and regenerated
content before comparing. Live dispatch state remains rendered in the
snapshot for humans and remains available via the snapshot data object /
CLI for dashboards; it is simply not gate-relevant, because freshness of
ephemeral, machine-local state is not a meaningful CI signal.

## Consequences

### Positive

- The gate fires only on genuine aggregation drift (backlog/grade counts,
  triaged list, specs, decisions, telemetry) — its actual purpose.
- FEAT-205's observability section is preserved unchanged.
- Deterministic across machines and across time; no daily false-fails.

### Negative

- Drift within the Dispatch lifecycle section itself is invisible to the
  gate. Acceptable: that section is live state, not durable memory, so
  "staleness" there is expected rather than a defect.
