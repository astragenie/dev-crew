# DEC-072: provider-only capture/recall transport + one GEPA event vocabulary

## Context

Two CLI-spawn modules survived from the pre-`@astragenie/astramem-client` era:
`memory-bridge.mts` (`emit()` — a provider-first send with a `resolveCli()` +
`spawn` fallback for GEPA trainset events) and `memory-recall.mts`
(`recallPrior()` — already orphaned by FEAT-231, which converged reviewer/wave
recall onto the client's `recallSilent`). `memory-sink.mts::recordMemory` had
an identical, independent CLI-spawn fallback (`recordViaCliFallback`) for
decision/lesson/note/failure capture. FEAT-235 finishes the astramem-client
migration GH #363 / #365 started: every capture and recall call in this repo
now goes through the shared client, and both CLI-spawn modules are deleted.

The pre-migration `emit()` also had a live bug: its provider-path send set
`type: payload.event` — a free GEPA vocabulary string
(`slice_close|phase_gate_fail|slice_started|triage_shift|recall_used`) — on
the wire, instead of the closed `MemoryKind` enum
(`decision|lesson|note|failure`, `memory-sink.mts`) the #365 Q4 decision
established as the one vocabulary. This DEC also resolves that split.

## Decision 1 — drop the CLI-spawn capture fallback entirely. Accepted.

`@astragenie/astramem-client`'s `resolveWireProvider()`
(`node_modules/@astragenie/astramem-client/dist/resolve.js:146-198`) is a
verified strict superset of `resolveCli()`'s discovery chain: the same
`CLAUDE_PLUGIN_ROOT_MEMORY` env read, the same `where`/`which` PATH probe
gated by the same `ASTRAMEM_DISABLE_PATH_PROBE` test-isolation flag — plus two
earlier, stronger strategies `resolveCli()` never had (dep-mode selector
import, dep-mode local/saas provider probe). A repo where `resolveCli()`
would have found the CLI today is a repo where `resolveWireProvider()` also
finds a provider today. Dropping the redundant spawn is therefore not a
fail-open regression — no repo loses capture capability it had before.

`memory-bridge.mts::emit()` and `memory-sink.mts::recordMemory`'s
`recordViaCliFallback` (the same pattern, independently implemented) are both
retired on this basis. `memory-bridge.mts` and `memory-recall.mts` are
deleted outright.

## Decision 2 — closed MemoryKind wins; explicit event -> kind map

GEPA capture moves to a new leaf, `src/scripts/lib/memory-gepa.mts`, owning
`GepaPayload`, `buildGepaMetadata()` (moved verbatim — pure, unit-tested), and
one exported `emitGepaEvent(payload, capMs?)` that calls the shared
`sendViaProvider` directly with `type` set through this mapping (not the raw
event string):

| GepaPayload.event | -> MemoryKind | Rationale |
|---|---|---|
| `slice_close` | `lesson` | `buildCloseFeedback` is dominated by lessons_learned/surprises — closest existing kind |
| `phase_gate_fail` | `failure` | Direct semantic match — a gate failure |
| `slice_started` | `note` | Purely informational bookkeeping, no judgment content |
| `recall_used` | `note` | Telemetry (`hits=<n>`), not a decision/lesson/failure |
| `triage_shift` | `decision` | Zero current callers (dead scaffold field) — mapped for forward-compat only |

`emitGepaEvent` threads `capMs` from the caller, defaulting to
`memory-transport.mts::DEFAULT_MEMORY_CAP_MS` (DEC-071's shared cap policy) —
never a locally re-hardcoded literal.

`--metadata` (now the provider payload's `metadata` field) stays WRITE-ONLY:
astramem's `RecallHitSchema` has no `metadata` field, so nothing placed there
ever comes back out via recall. This was true before this DEC and remains
true after — GEPA capture doesn't depend on recall fidelity through astramem
(the GEPA optimizer reads its own local JSONL store, never astramem).

## Decision 3 — memory-doctor.mts stays CLI-based (amendment to the original contract)

The architect contract that scoped this FEAT (SLICE-5) proposed collapsing
`memory-doctor.mts` onto the client's coarse `HealthResponse { ok: boolean }`,
accepting a named regression: loss of the 6-state health enum
(`ok|unreachable|not_configured|unknown|cli_missing|disabled`) and the
`rejected_count`-derived signal. That regression was **rejected** at build
time — `memory-doctor.mts` is consumed by `loop-installer.mts`
(`probeMemory` -> `renderMemoryStatusBlock`, an install-time diagnostic) and
its richer signal set has real operational value with no client equivalent
(`resolveWireProvider()` resolves an in-process `WireProvider` object; its
`health()` only reports `{ ok }`, nothing like the real
`astramem doctor --json` shape: `env_vars` / `local_url_source` /
`pending.rejected_count` / `deprecation_hits`).

Instead: `memory-doctor.mts` keeps spawning `astramem doctor --json` and
returning the full `MemoryStatus` shape, byte-identical to before this FEAT.
Its `resolveCli()` dependency — previously imported from `memory-bridge.mts`
— was extracted into a small standalone leaf,
`src/scripts/lib/astramem-cli-resolver.mts`, before `memory-bridge.mts` was
deleted. This is the ONE legitimate CLI-path consumer surviving FEAT-235: a
diagnostic probe, not a hot capture/recall path, with no astramem-client
equivalent for its rich output shape.

## Consequences

- Every capture path (grade-writer, phase-gate x2, start-slice x2,
  memory-sink's decision/lesson/note/failure writers) and every recall path
  (reviewer/wave via FEAT-231, slice-start recall) now goes through
  `@astragenie/astramem-client` exclusively. Zero `resolveCli`/`spawn`
  astramem path remains outside `astramem-cli-resolver.mts` and its one
  consumer, `memory-doctor.mts`.
- `memory-bridge.mts` and `memory-recall.mts` are deleted, along with their
  test files. Coverage for `resolveCli()`'s discovery chain moved to
  `astramem-cli-resolver.test.mts` (still real coverage — this logic survives
  as a leaf, not dead code). GEPA event-mapping coverage moved to
  `memory-gepa.test.mts`.
- The GEPA wire vocabulary bug (`type: payload.event` instead of the closed
  `MemoryKind`) is fixed: every GEPA capture now sends a `MemoryKind`-valid
  `type`, consistent with `memory-sink.mts`'s writers.
- `memory-doctor.mts`'s output shape and health-signal richness are
  UNCHANGED — no regression, contrary to the original contract's SLICE-5
  proposal. `loop-installer.mts` / `memory-doctor-renderer` keep working
  identically.
- Fail-open contract preserved everywhere: every migrated path stays
  never-throws / byte-identical-when-off. `DEFAULT_MEMORY_CAP_MS` (DEC-071)
  remains the single source of truth for capture caps, including the new
  `memory-gepa.mts` path.
