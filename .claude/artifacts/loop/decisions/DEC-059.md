# DEC-059: GEPA optimizes an addressable portable-core block, not the whole prompt file

## Context

`gepa-core/src/types/candidate.ts` keys `Candidate` on whole-file identity:
`prompt_path` (which `.md` on disk) and `prompt_hash` (a hash of the entire
rendered file). If GEPA's candidate generator and judge fitness function are
ever pointed at that whole file, every Claude-Code-specific detail baked into
it — frontmatter `Tools:` grants, `${CLAUDE_PLUGIN_ROOT}` path expansions,
`model:` tier hints, dispatch-prompt wiring — becomes part of the
fitness-selected text alongside the actual role prose (persona, quality bar,
reasoning approach). A high-fitness candidate could win by degrading platform
wiring, or a good prose mutation could be discarded because it collided with
unrelated wiring noise in the same hash.

This is exactly the risk ADR-B (same retrospective, §5) already named for the
narrower "portable agent core" extraction covering researcher/architect/
document-writer: role IO contracts and quality bars are genuinely portable
across platform bindings (Claude Code today; a second binding is plausible
per the 18–24-month vision in §3.3); tool wiring and path expansion are not.

The decision is free today and expensive later: zero trial JSONL exists in
either repo's history (`gepa-core` + `dev-team` GEPA skills, 908 commits
scanned — retrospective §0.2 finding 2), `GEPA_LIVE_GENERATOR` is unset, and
FEAT-210 (`GEPA capture canary + judge/held-out prerequisites`, this repo's
`.claude/artifacts/loop/backlog/triaged/FEAT-210.md`) explicitly gates its
own acceptance criteria on this ADR landing "BEFORE any GEPA_LIVE_GENERATOR
enablement." Once real trial data and candidate history accumulate against a
whole-file schema, migrating to a block-scoped schema means re-deriving
fitness history from raw text — this DEC exists to avoid that migration.

## Decision

We will:

1. **Delimit an addressable portable-core block** inside each optimizable
   agent prompt file with an explicit marker pair:
   ```
   <!-- gepa:portable-core:start -->
   ...role persona, IO contract, quality bar, reasoning approach...
   <!-- gepa:portable-core:end -->
   ```
   Everything inside the markers is optimizer-visible. Everything outside is
   not.
2. **GEPA's candidate generator extracts and mutates only the delimited
   block.** Rendering a candidate back into a runnable agent file is a
   splice operation: take the current on-disk file for a given platform
   binding, replace the content between the markers with the candidate's
   block content, leave everything outside untouched.
3. **The judge scores the block's effect on task fitness**, not incidental
   diffs in wiring that the splice never touches.
4. **This record lands before `GEPA_LIVE_GENERATOR` is ever flipped on**,
   per FEAT-210's acceptance criteria — there is zero trial history to
   migrate, so the schema change is additive-only at this point in time.

### Candidate schema change

`gepa-core/src/types/candidate.ts` gains one field and repurposes two:

- `target_block: string` — new. Block identifier within the file (e.g.
  `"portable-core"`). Single fixed value for v1 (one block per file);
  declaring it as a field now — rather than hardcoding the marker name in
  the generator — avoids a second schema break if/when multi-block files
  are ever needed (see Revisit trigger below).
- `prompt_path: string` — unchanged meaning: which file this candidate's
  platform-bound rendering targets or was extracted from.
- `prompt_hash: string` — scope narrows: hashes the **extracted block
  content only**, not the whole rendered file. This is the value fitness
  history and dedup key off. A field named `rendered_file_hash` (or
  equivalent, non-normative here) may be added separately if judges need a
  whole-file audit hash for reproducibility — that's an implementation
  detail for the FEAT-210 build, not part of this ADR's schema contract.

## Consequences

### Positive

- Fitness-selected text is role prose only; a candidate can never win or
  lose on wiring it never touched.
- Whole-file provenance (`prompt_path`) is retained for audit — candidates
  still know which file and platform binding they came from.
- The schema change is additive and lands on zero trial history — no
  migration, no backfill, no stale-candidate reconciliation.
- Directly unblocks FEAT-210 AC 4 ("Record ADR-C... BEFORE any
  GEPA_LIVE_GENERATOR enablement").

### Negative

- Candidate generation needs a block-extraction/splice step that doesn't
  exist yet — real implementation cost lands in the FEAT-210 build, not
  free with this record alone.
- Every optimizable agent file needs the marker pair added by hand once;
  a validator should confirm markers are well-formed and unique per file
  (not scoped here — FEAT-210 build concern).

### Neutral

- Files with no markers are simply not GEPA-optimizable candidates yet;
  this is consistent with ADR-B's narrow initial scope (researcher,
  architect, document-writer only).

## Alternatives considered

- **Whole-file optimization (status quo)** — cheaper right now: no
  extraction step, `prompt_hash` already means "the whole file." *Why
  rejected*: bakes `Tools:`, `${CLAUDE_PLUGIN_ROOT}` expansions, and
  `model:` hints into fitness-selected text; once trial data accumulates
  against this schema, unwinding it means re-deriving fitness history from
  raw diffs — exactly the asymmetry this record exists to avoid.
- **Full YAML→codegen pipeline now** (early graduation of ADR-B's kernel
  package) — would give a clean single source of truth per role. *Why
  rejected*: ADR-B already ruled this out as premature (WP4 anti-purity
  verdict — no GEPA trial data to protect, no second platform binding
  exists). Building codegen before there is a second consumer to validate
  the abstraction against is the same YAGNI mistake ADR-B avoided; this DEC
  does not reopen that call.
- **Defer this decision until GEPA go-live is imminent** — avoids doing
  design work now for a system that has never run. *Why rejected*: the
  retrospective's own framing (§5 ADR-C context) is that this decision is
  free today and expensive after data accumulates — deferring converts a
  free decision into a migration.
- **Multiple named sub-blocks per file (fine-grained optimization units)**
  — e.g. separate persona / quality-bar / reasoning blocks, each
  independently optimizable. *Why rejected* for v1: adds generator and
  judge complexity with no second consumer to validate the finer
  granularity against; `target_block` is declared as a field specifically
  so this remains possible later without another schema break, but v1
  ships one block per file to match ADR-B's already-scoped 3-role
  extraction.

## Revisit trigger

Re-open this decision if **a second platform binding materializes** — the
same trigger ADR-B names for graduating the portable-core extraction into a
real kernel package. A second binding is the first point where block-level
splicing (single marker pair, single rendering target) might prove
insufficient — e.g. if the two bindings need materially different
non-portable wiring shapes around the same block, or if per-binding
rendering needs more than a flat splice. Until then, one block per file,
spliced per platform, is the right-sized answer to a problem with zero
production evidence.
