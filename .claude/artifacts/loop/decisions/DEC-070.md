# DEC-070: cadence trigger — `loop.mts retrospective` completion

## Context

FEAT-229 wires the already-shipped continuous-learning pieces (FEAT-221
`mineFailures`, FEAT-222 `generateEvalsForClusters`) into one orchestrator,
`runLearningCycle` (`src/scripts/lib/learning-cycle.mts`). The FEAT's own
"Scope B" section required picking exactly one cadence surface without adding
new scheduler infrastructure, and recommended option **(a)**: integrate into
the existing marathon-checkpoint / retrospective flow.

Two candidate hook points inside that flow were considered:

1. **`checkMarathonCheckpoint`** (`marathon-checkpoint.mts`) or its consumer
   `checkStopConditions` (`stop-conditions.mts`) — this is evaluated on
   *every* `checkStopConditions` call (via `Promise.all` in
   `gatherStopInputs`), which itself runs on every `/runner:brief`, every
   auto-loop iteration boundary, and other read-only status checks. Firing a
   learning cycle there would run it far more often than "a checkpoint/retro
   fires" implies — it is a pure signal-computation function with no side
   effects today, and turning it into a trigger point would run
   `runLearningCycle` on every status poll, not just when a retrospective
   actually lands.
2. **`loop.mts`'s `retrospective` subcommand** — the actual write path
   invoked by `/runner:retrospective` (and the fallback remedy the
   marathon-checkpoint hard-stop blocker already tells the operator to run:
   `` Run `/loop:retrospective` to capture lessons before continuing. `` —
   see `applyMarathonCheckpointSignal` in `stop-conditions.mts`). This only
   runs once per actual retrospective, matching "run a cycle when a
   checkpoint/retro fires" literally: a retro *fires* here, not on every
   status check.

## Decision: hook into the `retrospective` CLI subcommand. Accepted.

`src/scripts/loop.mts`'s `retrospective` handler now calls
`runLearningCycle(repoPath, config)` immediately after `writeRetrospective`
succeeds, merging the result onto the command's return value as
`learningCycle`. This is the sole cadence trigger (B-a); no new
`CronCreate` schedule (B-b) and no post-slice-close hook (B-c) were added.

Rationale:

- **Matches the existing reflection point exactly.** A retrospective is
  already the loop's designated "look back and consolidate" moment
  (marathon-checkpoint's own hard-stop remedy). Running the learning cycle
  there means every retro also refreshes the failure-cluster / eval-spec
  state, with no new operator action.
- **Fires once, not on every poll.** Unlike `checkMarathonCheckpoint` (a pure
  read evaluated on nearly every stop-condition check), `retrospective` is an
  explicit write action the operator or the hard-stop flow triggers
  deliberately — the natural cadence boundary.
- **No new infrastructure.** No cron registration, no new hook file — a
  single call added to an existing command handler.
- **Fail-silent by construction.** `runLearningCycle` returns `null`
  (opt-in, AC-3) or a result object; it never throws (AC-2), so the
  retrospective's own success path is never put at risk by the learning
  cycle.

## Consequences

- `loop.mts learn` remains the standalone operator-invocable entry point
  (runs one cycle immediately, independent of any retrospective).
- Repos that never run `/runner:retrospective` (and never hit the
  marathon-checkpoint hard stop that mandates one) never get an automatic
  learning cycle — this is an accepted gap, not a bug: `loop.mts learn` is
  always available as a manual trigger, and `loop.learningLoop.enabled`
  defaults to `false` regardless of cadence (AC-3).
- If a future FEAT wants a cycle to run at slice-close cadence instead of
  (or in addition to) retro cadence, that is option (c) from FEAT-229's
  scope and would need its own DEC — not silently folded into this one.
- AC-6 satisfied by this record.
