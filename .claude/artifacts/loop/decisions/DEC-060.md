# DEC-060: workflow-state.json gains additive schemaVersion; loop refuses its cross-plugin pin-write on mismatch; crew-side load validation requested upstream

## Context

`docs/research/2026-07-02-architecture-retrospective.md` §5 ADR-D and
FEAT-209 (`.claude/artifacts/loop/backlog/triaged/FEAT-209.md`) name a
live gap in the cross-plugin state-write contract DEC-018/DEC-019
deliberately accepted: crew's `WorkflowStateSchema` (Zod,
`dev-team/scripts/lib/schemas.ts:69-76`) is defined but never invoked —
`loadWorkflowState` (`dev-team/scripts/lib/workflow-state.ts:115-138`)
does raw `JSON.parse(workflowText) as WorkflowState` with the comment
"State file is always written by this module; shape is trusted"
(`:121-123`). Loop writes into that same file from two call sites it
owns:

- `src/scripts/lib/session-drift.mts::writeSessionIdToWorkflowState`
  (`:77-100`) — the session-pin writer, dispatched from
  `src/scripts/lib/slice-linker/start-slice.mts::pinSessionId` (`:197-203`).
- `src/scripts/lib/slice-linker/start-slice.mts::writeWorktreePathToState`
  and `::rollbackWorktreePathInState` (`:212-250`) — the worktree-persistence
  writer DEC-019's failure-atomicity invariant governs.

Both duplicate an inline read → `JSON.parse` → mutate → `fs.writeFile`
block against `.claude/state/crew/workflow-state.json`, and both
silently substitute a blank `{ version: "1.0", currentRun: {} }` state
on *any* parse failure — indistinguishable from "file missing." That
conflation is the exact corruption class behind the one recorded
incident: the 2026-06-10 session-hang rebuild (FEAT177/SLICE88,
~117 min / 85M tokens), whose only trace anywhere is a self-reported
`reconcileNote` field inside the live state file itself — no external
postmortem artifact exists (retrospective F-13).

Three options were evaluated for closing this gap from loop's side:

- **(A) Loop rejects any workflow-state.json missing `schemaVersion`.**
  Treat absence as "unknown, therefore incompatible."
- **(B) Defer entirely to the upstream request — no loop-side change now.**
  Land only crew-side Zod validation, tracked as a future dev-team release.
- **(C) Loop-side `schemaVersion` guard on both write sites now, with a
  shared read helper that also stops the parse-failure↔missing-file
  conflation; crew-side load validation filed as a separate
  upstream-request, not implemented here.**

## Decision

We will adopt **(C)**. `workflow-state.json` gains one additive
top-level field, `schemaVersion: number`, sibling to the existing
`version`/`updatedAt`/`currentRun`/`recentRuns` keys. A file with no
`schemaVersion` key is treated as implicitly `schemaVersion: 1` (AC-1)
— this covers every file on disk today and every file crew writes
before it adopts the upstream request below.

A new shared module, `src/scripts/lib/workflow-state-guard.mts`,
exports:

```ts
export const LOOP_SUPPORTED_WORKFLOW_STATE_SCHEMA_VERSION = 1;

export class WorkflowStateSchemaMismatchError extends Error {
  constructor(message: string) {
    super(message);
    this.name = "WorkflowStateSchemaMismatchError";
  }
}

export class WorkflowStateCorruptError extends Error {
  constructor(message: string) {
    super(message);
    this.name = "WorkflowStateCorruptError";
  }
}

export async function readWorkflowStateForWrite(
  statePath: string
): Promise<{ state: any; existed: boolean }>;
```

`readWorkflowStateForWrite` replaces the duplicated inline read block
in all three write functions:

- `fs.readFile` rejects with `ENOENT` → returns
  `{ state: { version: "1.0", currentRun: {} }, existed: false }` —
  unchanged from today, matches DEC-018's create-on-absent scaffold.
- `fs.readFile` succeeds but `JSON.parse` throws → throws
  `WorkflowStateCorruptError` with a message naming `statePath`, the
  parse error, and a repair hint ("repair or delete the file manually,
  or restore from git/backup, then retry"). This is the AC-3 fix: the
  function no longer silently discards `recentRuns` and any other
  existing content by falling back to a blank state.
- Parse succeeds → reads `state.schemaVersion ?? 1`; if that value is
  greater than `LOOP_SUPPORTED_WORKFLOW_STATE_SCHEMA_VERSION`, throws
  `WorkflowStateSchemaMismatchError` naming `statePath`, the file's
  `schemaVersion`, and the version loop supports (AC-2). Otherwise
  returns `{ state, existed: true }`.

Propagation differs by call site, matching each site's **existing**
error-handling contract rather than inventing a new one:

- `writeSessionIdToWorkflowState` is fail-open by design (DEC-018;
  `pinSessionId`'s comment: "best-effort — never blocks slice start").
  It catches `WorkflowStateSchemaMismatchError` /
  `WorkflowStateCorruptError` specifically (not folded into the
  generic catch used for transient I/O errors), logs the error's
  `name` + message via `console.error` so the refusal is visible in
  the slice-start transcript, and returns without writing. Slice-start
  is not blocked; the write is refused and the refusal is loud, not
  silent — satisfying AC-2/AC-3 without weakening DEC-018's guarantee.
- `writeWorktreePathToState` / `rollbackWorktreePathInState` are
  fail-loud by design (DEC-019's failure-atomicity invariant already
  throws before writing on a null `sliceFile`). Both new error types
  propagate unchanged to `applyWorktreeResult`'s caller — consistent
  with a function whose whole contract is atomic-or-throw.

Crew-side load validation (invoking the existing `WorkflowStateSchema`
inside `loadWorkflowState`, and crew publishing/bumping its own
`schemaVersion`) is **not implemented here** — it is filed as
`docs/upstream-requests/2026-07-02-hero-crew-workflow-state-load-validation.md`
against hero-crew/dev-team, per FEAT-209 AC-4.

## Consequences

### Positive

- Converts the exact silent-corruption class behind the 2026-06-10
  incident into two loud, named, catchable errors instead of a
  swallowed `JSON.parse` throw.
- `schemaVersion` is purely additive — every file on disk today (no
  key present) keeps working with zero migration.
- Each write site keeps its own pre-existing failure philosophy
  (fail-open session-pin vs. fail-loud worktree-persist) instead of
  forcing one contract onto both, so DEC-018 and DEC-019 stay valid as
  written.
- Unblocks ADR-D's loop-side half independently of hero-crew's release
  cadence — the upstream request can land whenever dev-team schedules
  it without gating this fix.

### Negative

- Two call sites still duplicate the constant `.claude/state/crew/workflow-state.json`
  path segments (`STATE_PATH` in `session-drift.mts`,
  `STATE_PATH_PARTS` in `start-slice.mts`) — this decision does not
  consolidate them beyond routing both through the same read helper;
  full de-duplication is a separate, optional cleanup.
- Until the upstream request lands, crew itself still trusts the file
  shape unconditionally at load — this decision only protects the
  write side loop owns, not the read side crew owns. The divergence
  risk DEC-018 already accepted is narrowed, not eliminated.
- `LOOP_SUPPORTED_WORKFLOW_STATE_SCHEMA_VERSION` needs a manual bump
  (and a `MIN_CREW_VERSION`-style pin) whenever crew ships a schema
  change loop must understand — new discipline joins the existing
  `MIN_CREW_VERSION` cross-plugin contract surface, per ADR-D
  "Consequences."

### Neutral

- `writeSessionIdToWorkflowState`'s refusal is observable only via
  `console.error` in this decision's scope — no structured telemetry
  event. If refusal frequency needs to be measurable later, that is
  additive work, not a blocker here.

## Alternatives considered

- **(A) Reject any file missing `schemaVersion`.** Simplest guard
  logic. *Why rejected*: directly contradicts FEAT-209 AC-1 ("absent =
  implicitly v1, proceeds without refusal") and would refuse every
  workflow-state.json in existence today, since hero-crew has not
  shipped the field yet — the guard would fire on 100% of writes from
  day one.
- **(B) Defer entirely to the upstream request; no loop-side change
  now.** Zero implementation cost today. *Why rejected*: leaves the
  parse-failure↔missing-file conflation and the unguarded cross-plugin
  write live in the exact code loop already owns and can fix without
  waiting on another repo's release; the retrospective frames this
  specifically as a "quick win" loop can ship independently (top-10
  #7), and FEAT-209's own scope is loop-side-guard-now,
  upstream-request-separately — not loop-side-later.
- **(C) Loop-side guard now (both write sites) + separate upstream
  request for crew-side load validation.** Selected. See Decision above.
