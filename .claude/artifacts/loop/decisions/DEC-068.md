# DEC-068: EvalGenerator target contract (pin, not implementation)

## Context

FEAT-222 is gated on an unambiguous target contract before build. The
architect-review already resolved WHICH crew artifact to target
(`evals/agents/*.yaml`, not gepa-core Trial JSONL — see FEAT-222's own
"Target artifact — RESOLVED" section). What remained open: the exact YAML
fields, per-agent file routing, the `manufactured` marker convention, the
`failure_class → agent-under-test` table, and where provenance lives.
Investigated against the real crew source (`C:/work/mega/dev-team`):
`evals/cli.ts`, `evals/lib/run-eval.ts`, all 9 `evals/agents/*.yaml` files,
and `gepa.config.json`.

## Decision

### 1. Schema tolerance — no upstream request needed

`evals/lib/run-eval.ts` parses each spec with `parseYaml(raw) as EvalSpec`
— a bare TypeScript type assertion, not a Zod/runtime schema. Assertions do
not check for excess properties, at any nesting depth. Real precedent
already in the repo: `held_out: true` appears on test entries in
`crew-refactor.yaml`, `crew-integrator.yaml`, `crew-verifier.yaml` even
though `EvalTest` (run-eval.ts:28-32) has no `held_out` field — it is
read by no code path (confirmed: zero non-comment matches for `held_out`
in `evals/lib/**/*.ts` outside the unrelated `.gepa` `EvalCase` shim
objects). `crew-release-engineer.yaml:91-93` even comments on this
explicitly: "evals/agents/*.yaml has no held_out field like the
`.gepa/eval/*.jsonl` EvalCase schema... held out in spirit only."

**Conclusion: additive test-level fields (`manufactured`, `provenance`)
are safe, load cleanly, run identically to hand-authored tests, and do NOT
require a crew-side schema change or an `docs/upstream-requests/` doc.**
This is the same tolerant-cast pattern DEC-067 relied on for `remember`'s
non-strict response schema, applied on the write side instead of the read
side.

### 2. Field placement: per-TEST, not per-file

Provenance and the marker go on the individual `tests[]` entry, not at
the top of the YAML file. Rationale: multiple manufactured cases (from
different clusters, over time) can accumulate inside the same
`evals/agents/crew-<agent>.yaml` file, colocated with hand-authored tests
in the same `tests:` array — a file-level field could only describe one
manufactured case. This exactly mirrors the existing `held_out` field,
which is also test-level.

Generated test shape (fields beyond `name`/`fixture`/`assert` are inert to
`run-eval.ts` and exist for provenance/dedup only):

```yaml
  - name: manufactured-<failure_class>-<cluster_hash>
    manufactured: true
    provenance:
      generator: loop-eval-generator
      failure_class: <FailureClass>              # e.g. review_fail
      cluster_hash: <sha256(failure_class + "::" + normalizeRootCause(representative_root_cause)).hex.slice(0,16)>
      source_run_id: <FailureCluster.exemplar_ids[0]>
      generated_at: <ISO-8601>
    fixture: file://evals/fixtures/manufactured-<cluster_hash>.txt
    assert:
      - type: llm-rubric
        rubric: "<derived from FailureCluster.representative_fix / recommended_fix — must name the concrete root cause and the expected corrected behavior, same voice as hand-authored rubrics in the target file>"
```

The fixture file is a new plain-text fixture (candidate-output shape,
matching `loadFixture`'s plain-text branch) built from
`representative_root_cause` + enough surrounding context to be a
standalone replay case — written alongside the YAML edit.

### 3. Per-agent file routing — append into the EXISTING per-agent file

`findSpecByPromptId` (run-eval.ts:657-675) returns the FIRST file in
`evals/agents/` whose `prompt_id` matches. If a manufactured spec were
written to a **new**, separate file sharing a `prompt_id` with an existing
file, only one of the two would ever be picked up by `bun run evals
--prompt <id>` — silently orphaning the other and violating AC-5
("participate exactly like hand-authored ones, no special-casing").

**Decision: the generator APPENDS a new entry to the `tests:` array of the
existing `evals/agents/crew-<agent>.yaml` file for the mapped agent.**
Never create a second file for a `prompt_id` that already has one.

Filename convention confirmed from the 9 existing files: `evals/agents/
crew-<agent>.yaml`, where `<agent>` = `prompt_id` = the agent prompt's
basename under `agents/<agent>.md` (e.g. `crew-refactor.yaml` →
`prompt_id: refactor` → `agents/refactor.md`, NOT `crew-refactor`).

### 4. `manufactured` marker convention

Top-level boolean `manufactured: true` on the test entry (see template
above). No separate "synthetic" enum needed — boolean is sufficient and
matches `held_out`'s boolean precedent. AC-5's "visibly marked" is
satisfied at the source level (a human reading the YAML sees it
immediately, same as `held_out`); the eval viewer
(`evals/viewer/index.html`) renders no special treatment for `held_out`
either, so no viewer change is required or expected for `manufactured`.

### 5. `failure_class → agent-under-test` mapping table

Cross-referenced FEAT-220/221's 9-value `FailureClass` enum
(`src/scripts/lib/learnings.mts:104-114`) against the 9 real
`evals/agents/*.yaml` files in dev-team. Only map where the failure class
maps cleanly to ONE agent's prompt behavior — ambiguous classes are
intentionally left undefined (AC-4's skip path is a normal, expected
outcome, not a gap to be closed later):

| failure_class          | agent-under-test    | file                              | rationale |
|-------------------------|---------------------|------------------------------------|-----------|
| `review_fail`           | `reviewer`           | `evals/agents/crew-reviewer.yaml`   | review pipeline missed/misjudged something — reviewer's own prompt behavior |
| `validation_fail`       | `verifier`           | `evals/agents/crew-verifier.yaml`   | validation gate misjudged pass/fail — verifier's own prompt behavior |
| `hallucinated_ref`      | `refactor`           | `evals/agents/crew-refactor.yaml`   | refactor already owns stale-ref/dead-ref detection as a first-class concern (see its `stale-ref-false-negative` test) |
| `bad_patch`             | `fullstack-dev`      | `evals/agents/crew-fullstack-dev.yaml` | fullstack-dev is the default/general builder variant in this loop's orchestrator dispatch (CLAUDE.md "Orchestrator mode") |
| `bad_tool_use`          | *(undefined — skip)* | —                                   | can originate from any dispatched agent; no single owning eval file |
| `ignored_policy`        | *(undefined — skip)* | —                                   | too broad (spans release, security, scope policies); no single owning eval file |
| `stale_context`         | *(undefined — skip)* | —                                   | overlaps `hallucinated_ref`'s refactor mapping; not a distinct prompt-quality signal on its own |
| `subagent_incomplete`   | *(undefined — skip)* | —                                   | orchestration/dispatch-lifecycle failure, not a prompt-quality issue an eval rubric can exercise |
| `other`                 | *(undefined — always skip)* | —                            | catch-all with no derivable rubric by definition |

4 of 9 classes map; 5 are intentionally undefined. This table lives in
`eval-generator.mts` as a plain `Record<FailureClass, string | undefined>`
— extending it later (e.g. once `evals/agents/crew-architect.yaml` exists,
or once `ignored_policy` earns a dedicated eval owner) is additive, not a
contract break.

### 6. Provenance / dedup

`cluster_hash = sha256(failure_class + "::" + normalizeRootCause(representative_root_cause)).hex.slice(0, 16)`,
reusing FEAT-221's existing `normalizeRootCause` (lowercase, collapsed
whitespace, 160-char truncation) so the hash is stable across re-runs even
if a cluster's `count`/`exemplar_ids` drift between generator invocations.
AC-3 dedup check: before appending, the generator parses the target
file's existing `tests[]` and skips (no write, no error) if any existing
entry's `provenance.cluster_hash` already matches.

`source_run_id` = `FailureCluster.exemplar_ids[0]` — already a
descriptive composite id from failure-classifier.mts (e.g.
`learning-<id>`, `<sliceId>@<ts>`, `<agent>@<ts>`); no new id scheme
needed.

### 7. Cross-repo write target — the gap the architect-review didn't pin

`evals/` and `agents/*.md` live in crew's SOURCE repo (`dev-team`), not in
every repo that installs the crew plugin — GEPA eval/optimize is crew's
own self-improvement loop over its own prompts, not something crew ships
into consumer repos. Loop dogfoods this repo's own build against crew's
dispatched agents; C:/work/mega/dev-team is a sibling checkout in this
dev environment, same pattern as the Astragenie.Standards sibling-path
convention in CLAUDE.md — but nothing in `.claude/loop.json` currently
names it, and this repo's existing cross-plugin convention for asking
crew for something is `docs/upstream-requests/` (see
`src/tests/injection-defense.test.mts`'s `target_repo:
astragenie/dev-team` frontmatter) — a human/PR-mediated channel, NOT a
live filesystem write.

**Pinned: the generator requires a new `loop.crewRepoPath` config key in
`.claude/loop.json`** (absent by default) pointing at a local crew
checkout containing `evals/agents/`. If unset, or the path/`evals/agents/`
subdirectory doesn't exist, the generator skips ALL clusters with a
logged reason (`crew repo not configured/found — see loop.crewRepoPath`)
— extending AC-4's never-throw contract to this precondition, not just
to per-cluster failure_class gaps. This is an operational integration
detail on loop's side (a config key loop reads), not a crew-side schema
question, so it does NOT need an `docs/upstream-requests/` doc.

### 8. Deferred: Trial JSONL path

Not pursued. `@astragenie/gepa-core`'s `TrialSchema.source` is a closed
`z.enum(["eval", "captured", "soak"])` — no `manufactured`/`synthetic`
value exists, and extending it would require an upstream PR to a THIRD
repo (gepa-core), a two-hop dependency FEAT-222 explicitly avoids by
targeting the YAML format instead. If a future FEAT wants failures
replayed as Trials (optimizer input, not eval-suite input), that PR must
land in gepa-core first; out of scope here, tracked only as a known
constraint per FEAT-222's own text.

## Consequences

- Builder can implement `eval-generator.mts` against a fully concrete
  contract: 4 mapped failure classes, exact YAML shape, exact file-routing
  rule (append, never fork), exact dedup key.
- New config surface: `loop.crewRepoPath` (design decision #7) must be
  added to `.claude/loop.json` schema/docs as part of the FEAT-222 build
  — not a pre-existing key.
- No crew-side change and no `docs/upstream-requests/` doc required for
  the YAML schema itself (decision #1) — crew's tolerant parsing already
  supports this without modification.
- AC-6 satisfied by this record.
