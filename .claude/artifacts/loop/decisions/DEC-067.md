# DEC-067: how `emit()` should persist to astramem

## Context

`memory-bridge.mts::emit()` invokes an astramem `ingest` subcommand that **does
not exist** (real surface: `ingest-transcript | recall | remember | health |
config | doctor | connect`). It spawns, gets "unknown subcommand", swallows it
under the fail-silent contract → the astramem mirror **persists nothing today**
(#324 findings, PR #328). Two candidates to fix FEAT-223:

- **(a)** upstream-request a generic single-event `ingest` subcommand (keeps
  emit()'s payload shape; blocks on an astramem release).
- **(b)** reshape emit() onto the existing, working `remember` subcommand.

## Decision: **(b) — reshape emit() onto `remember`.** Accepted.

Verified by architect-review 2026-07-06 against real astramem 0.6.0 source +
gepa-core. Rationale:

1. **No external release gate** — `remember` already works in the installed
   0.6.0 build (`memory-sink.mts` uses it correctly today).
2. **Forward-compatible with the CLI→MCP migration (#324)** — `remember` maps 1:1
   to the future MCP `remember` tool; a new *CLI* `ingest` (option a) invests in
   the path slated for replacement.
3. **Reuses the working write vocabulary** rather than adding a second one.

## Payload-mapping contract (implement in FEAT-223)

- `--type` ← `payload.event` (free string; `remember` does not validate `--type`).
- `--content` ← `sanitizeContent(payload.feedback)` (reuse memory-sink's 2000-char cap).
- `--metadata` ← a **bounded** JSON object `{ sliceId, featId, score, phase,
  source, prompt_version, input: <summarized>, output: <summarized> }`. Do NOT
  forward `input`/`output` verbatim — cap nested strings (mirror memory-sink's
  sanitize pattern) to stay under the ~32KB Windows argv limit.

## Consequences (architect-review corrections — do not re-litigate)

- **`metadata` is WRITE-ONLY.** astramem's `RecallHitSchema` has no `metadata`
  field and the response schema is non-strict → Zod silently strips it. Nothing
  put in `--metadata` (or a hypothetical `ingest`) ever returns via `recall`, by
  any consumer. This is identical for option (a); it is NOT a reason to prefer
  (a). Do not design for structured round-trip via the CLI — it is impossible.
- **The GEPA optimizer never reads through astramem.** gepa-core's `fileStore()`
  reads/writes its own local JSONL directly; the astramem mirror feeds only
  `recallPrior()`→prompt-injection Markdown, not structured replay. So no
  fidelity is lost by flattening into `remember`.
- **Type vocabularies stay disjoint** — memory-sink's `MemoryKind`
  (decision|lesson|note|failure) and emit()'s `event` values coexist under one
  free-string `--type`; documented, not unified.
- **No `--agent`** — `GepaPayload` has no agent field; emit() events are not
  agent-scoped (retrofit later if agent-scoped GEPA recall is ever wanted).
- FEAT-223 becomes self-contained (no upstream blocker). FEAT-225 (`--project`)
  folds into the same `remember` touch — **and may already be resolved upstream**
  (0.6.0 `remember.ts` dated 2026-07-05 folds `--project`/`--agent` into
  metadata; verify against the live binary before building 225).
- Related but separate: `recallPrior()` is ALSO dead against the real CLI
  (`parseRecallOutput` expects a bare array; real CLI returns `{hits,…}`; and it
  checks `content` where the hit shape has `text`). Tracked as **FEAT-227**.
- Option (a) may still be filed as a low-priority upstream nicety, but the loop
  does not wait on it.
