# DEC-066: memory stack consolidates into crew via merge — runner schema is the seed

## Context

Two memory stacks are converging:

- **runner-plugin** already ships a materially complete, tested read/write memory
  stack: `memory-sink.mts` (write), `learnings.mts` / `learnings-ranker.mts`
  (decay+utility) / `learnings-decay.mts` / `learnings-citations.mts`,
  `decisions-store.mts`, `memory-recall.mts` + `recall-injector.mts` (astramem
  recall, now live).
- **dev-team (crew)** has an unstarted spec, **FEAT-188** ("MemoryProvider —
  capture/recall learning loop"), that proposes a NEW `src/lib/memory/` provider
  abstraction mirroring the gepa-core TrialStore pattern from a blank slate.

FEAT-219 (runner-side pre-work injection) and FEAT-188 (crew-side provider) both
touch the same capability. If they proceed independently the result is **two
drifting memory schemas** — already visible: three different `kind` enums exist
across the two repos, `severity` exists in neither runner module, and
`supersedes`/invalidate semantics exist only in FEAT-188's spec. The architect
review of FEAT-219 flagged this as the single most important decision to settle
before any slice is dispatched.

## Decision

1. **crew is the eventual single home** for the memory stack — it matches the
   existing hard-dependency direction (runner depends on crew via
   `MIN_CREW_VERSION`; crew is the base both plugins can import).
2. **The consolidation is a MERGE, not a handoff or a rebuild.** crew/FEAT-188
   MUST adopt runner's already-shipped, tested schema + rankers as the **seed**
   for `src/lib/memory/`, rather than authoring a fresh gepa-core-style
   abstraction. Runner's `MemoryKind`, `rankLearnings` (decay×utility), and
   `decisions-store` filtering are the canonical starting point; FEAT-188's net
   additions (`severity`, `supersedes`/invalidate, provider interface) are
   layered on top of that seed, not in place of it.
3. **FEAT-219 ships now on runner's existing schema** — it does not wait for the
   crew merge. FEAT-219 is the narrower runner-side adoption/wiring vehicle
   reusing the readers that already exist. The eventual move of those modules
   under crew is tracked separately (upstream-request + a crew-side slice), and
   FEAT-219 code is written so relocation is a move, not a rewrite.

## Consequences

- FEAT-219 SLICE-1 (write-side `agent_type` + `failure` kind) extends runner's
  `MemoryKind` — that same extension is the seed crew inherits, so the tagging
  is authored once.
- An upstream-request to hero-crew/dev-team is required: "adopt runner's memory
  schema as the FEAT-188 seed; do not rebuild." File before crew starts FEAT-188.
- Until the merge lands there are transiently two import paths; new code imports
  runner's modules and is structured for a later `crew:` relocation.
- Schema unification work (`kind` enum reconciliation, add `severity`, add
  supersede/invalidate) is a shared deliverable owned by whichever FEAT reaches
  it first, recorded against this DEC.
