# DEC-078: COND-B external-id stamping contract — CompositeProvider owns multi-tracker stamping; generic publishFeature/publishSlice stay id-only

## Context

Architecture review COND-B (`.claude/artifacts/crew/reviews/2026-07-09-tracker-provider-plan-review.md`,
finding 2) flagged that `TaskStoreProvider.publishFeature()` returns a single
external id, but a future `CompositeProvider` (FEAT-253, Phase 4) publishing
to both GitHub and Linear simultaneously must stamp **both**
`github_issue:`/`github_url:` and `linear_issue:`/`linear_url:` into FEAT/
SLICE frontmatter. FEAT-252's SLICE-1 (this slice) is required to decide the
contract before any LinearProvider write-method code lands (SLICE-157),
since Phase 4 implements the same DEC rather than inventing its own.

### Where stamping actually happens today (read before deciding)

Tracing `github_issue`/`github_url` writes end-to-end
(`grep -rn "github_issue" src/scripts scripts` plus manual read of
`scripts/lib/github-sync.mjs`, `scripts/lib/github-sync/issue-sync.mjs`,
`scripts/lib/github-sync/subissue-sync.mjs`,
`src/scripts/lib/task-store/providers/github-provider.mts`,
`src/scripts/loop.mts:729-765`):

1. `issue-sync.mjs`'s `createFeatureIssue` and `subissue-sync.mjs`'s
   `createSliceIssue` are **pure create** — they call `gh issue create` and
   return a bare issue number. No frontmatter write.
2. `GithubProvider`'s generic `TaskStoreProvider.publishFeature()`/
   `publishSlice()` (the interface methods) call those two functions
   directly and return the bare number — **also no frontmatter write**. The
   generic interface methods are already id-only/side-effect-free by
   construction, for GitHub, today.
3. The actual stamping — `mergeFrontmatter(...) + fs.writeFile(...)` writing
   `github_issue`/`github_milestone`/`github_url` — lives entirely inside
   `github-sync.mjs`'s own higher-level functions: `publishFeat`,
   `publishSlice`, `publishAll` (`github-sync.mjs:70-94, 111-121, 556-616`).
   `GithubProvider` exposes these as **GitHub-specific, non-interface**
   methods (`publishFeatureById`, `publishSliceById`, `publishAll`,
   `syncMilestones` — explicitly documented at
   `github-provider.mts:190-201` as "not part of the generic
   TaskStoreProvider interface").
4. The production call sites — `publishFeatureViaProvider`/
   `publishSliceViaProvider` in `loop.mts:740-765` — resolve the configured
   provider via `getProvider()` and then gate with
   `if (provider instanceof GithubProvider)`, calling the `...ById` methods.
   Any other resolved provider (today: `NoopProvider`, the all-throw/
   warning-stub `LinearProvider`) is a **silent no-op**: `return null`. No
   generic, provider-agnostic stamping call site exists yet.

Net: the generic interface contract (`publishFeature`/`publishSlice` →
bare id, no side effect) is **already the shape both existing providers
follow**. Stamping is entirely caller-owned, and today's sole caller
(`github-sync.mjs`'s high-level functions, reached through the
`instanceof GithubProvider` gate) is GitHub-specific by name and by field.

## Decision

**Option B — CompositeProvider owns stamping.** The generic
`TaskStoreProvider.publishFeature()`/`publishSlice()` interface methods
are NOT widened to return a per-provider id map. They keep their current
`Promise<number | string | null>` signature and stay pure create-and-return
— this matches what `GithubProvider` already does and what `LinearProvider`
(SLICE-157) will do. Frontmatter stamping remains entirely caller-owned,
exactly as it is today; `CompositeProvider` (FEAT-253) is simply a new
caller that knows how to stamp more than one provider's id.

Concretely, for FEAT-253 to build on:

1. `CompositeProvider.publishFeature(feat)` fans out `publishFeature(feat)`
   to each configured child provider (in configured order), collecting a
   local `{ [providerName]: { externalId, url } }` map — `url` is
   provider-derived (each provider already knows its own issue-URL shape;
   `GithubProvider`/`LinearProvider` expose it via their own `...ById`-style
   helpers or an equivalent small return-shape addition scoped to FEAT-253,
   not this DEC).
2. `CompositeProvider` performs **one** `mergeFrontmatter` + `fs.writeFile`
   per publish call, writing every succeeding child's id/url as
   `<providerName>_issue` / `<providerName>_url` (extending the existing
   `github_issue`/`github_url` naming convention naturally to
   `linear_issue`/`linear_url`). One merge call means one write — no
   double-write risk, since Composite is the *sole* fs writer for a
   composite-configured repo (solo-`github` and solo-`linear` configs never
   route through Composite at all).
3. A child that returns `null` (soft-fail: not configured, or the call
   failed) is skipped in the stamp map — its frontmatter field is left
   unset/unchanged, never written as `null`, so a later successful publish
   for that provider is not blocked by a stale null. Per COND-B's
   partial-failure requirement, Composite additionally logs a warn-level
   line distinguishing "provider not configured" (child resolved to
   `NoopProvider` / equivalent — no configuration present) from "provider
   configured but call failed" (child threw, or its own soft-fail warn
   already fired) — full warn-message contract and test matrix is FEAT-253
   AC-2/AC-3's job, not this DEC's.
4. Solo-provider publish (today's only live path, `github.enabled`/
   `taskStore.provider: "github"`) is **untouched**: `GithubProvider`'s
   existing self-contained `publishFeatureById`/`publishSliceById`/
   `publishAll` stamping stays exactly as-is. `LinearProvider` (SLICE-157)
   MAY grow an equivalent solo self-stamping `...ById` surface for parity
   if a solo-Linear production call site is wired up in that slice or a
   follow-up — that is SLICE-157/158 scope, not decided here.
5. `loop.mts`'s `instanceof GithubProvider` gate in
   `publishFeatureViaProvider`/`publishSliceViaProvider` will need a third
   branch for `CompositeProvider` when FEAT-253 lands (today's silent
   `return null` for "anything else" is correct only because nothing else
   exists yet that should actually publish). Recorded here as a known
   follow-up so FEAT-253 doesn't have to rediscover it.

## Consequences

### Positive
- Zero changes required to `GithubProvider`'s already-shipped, tested,
  idempotent stamping logic (`github-sync.test.mts` coverage stays valid
  untouched) — Option A (widen the interface) would have forced a rewrite
  of that logic to fit a new map-returning contract for no behavioral gain
  on the GitHub side.
- The generic interface stays exactly as simple as it already, in practice,
  is for both real providers — no new "two shapes of publishFeature"
  confusion for a future third provider (Jira, etc.) to reconcile.
- Field-naming convention (`<providerName>_issue`/`<providerName>_url`)
  is a mechanical extension of the existing `github_issue`/`github_url`
  pair — no frontmatter schema redesign, no migration for existing FEATs.

### Negative
- `CompositeProvider` duplicates a small amount of "call provider, collect
  id, merge frontmatter" orchestration that a map-returning interface
  would have pushed down into a single shared helper. Judged acceptable:
  the orchestration is a handful of lines and FEAT-253 already needs
  per-child warn-distinction logic that a generic helper couldn't fully
  own anyway (COND-B's not-configured vs failed distinction is
  Composite-specific policy, not reusable provider plumbing).
- Solo-Linear publish (if ever wired to a live call site) and
  Composite-Linear publish will use two different stamping code paths
  (a future `LinearProvider...ById` self-stamp vs `CompositeProvider`'s
  own merge) — mirrors the existing GitHub solo-vs-hypothetical-composite
  asymmetry, so it is a known, already-accepted shape rather than new risk.

### Neutral
- This DEC does not implement `CompositeProvider` — FEAT-253 does. It only
  binds FEAT-253's design to Option B so Phase 3 (this FEAT) and Phase 4
  don't diverge.

## Alternatives considered

- **Option A — widen `TaskStoreProvider.publishFeature()`/`publishSlice()`
  to return a structured `{ externalId, url }` (or a full per-provider map)
  and move stamping into one shared generic caller.** Rejected: would
  require refactoring `GithubProvider`'s working, tested `...ById`
  self-stamp methods (and the `instanceof GithubProvider`-gated call sites
  in `loop.mts`) to route through a new shared stamping path, for a
  provider pair (github + linear) where the *actual* need — Composite
  writing two sets of fields in one merge — does not require the generic
  single-provider interface to change shape at all. Higher blast radius
  for no behavioral gain outside Composite.
- **Option C — each provider stamps its own fields inside its own
  `publishFeature()`/`publishSlice()`, Composite just awaits both.**
  Rejected: reintroduces the double-write risk COND-B explicitly warned
  about (two independent `fs.writeFile` calls against the same frontmatter
  file in the same publish operation race on read-merge-write instead of
  going through one merge), and breaks the already-established convention
  that the generic interface methods are pure/id-only.
- **Option D — defer the decision to FEAT-253 itself.** Rejected: this is
  exactly what COND-B and FEAT-252's own AC ("STEP 1 ... before any code")
  forbid — Phase 3's `LinearProvider` write-method shape (SLICE-157) has to
  already match whichever contract Composite will assume.
