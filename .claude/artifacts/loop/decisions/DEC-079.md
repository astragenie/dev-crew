# DEC-079: Collision-proof slice-ID allocation - fetch-scan max+1 plus a renumber CLI for the residual race (FEAT-257)

## Context

Slice IDs are minted by a single call path: `createSlice()`
(`src/scripts/lib/backlog-store/slice-store.mts:311-343`) calls the private
`maxSliceIdUnder()` (same file, `:107-128`), which walks `slicesRoot(repoPath,
config)` - default `.claude/artifacts/loop/ai-loop/slices` - recursively,
regexes every filename against `/^SLICE[-_](\d+)/`, and returns the max
numeric id found. `createSlice` then allocates `sliceIdFor(maxId + 1)`
(`:130-132`) and writes the new slice file immediately (`:341`). This scan is
100 percent local-filesystem: it never runs `git fetch`, never reads
`origin/main`, and has no awareness of any other worktree or clone. There is
exactly one call site in production code
(`src/scripts/lib/slice-linker/feature-lifecycle.mts:228` and `:342`, the
single- and multi-slice materialization paths), both funneling through the
same `createSlice`.

Under wave mode, each parallel session runs in its own git worktree
(`src/scripts/lib/worktree-manager.mts`), each with its own independent
checkout of `slicesRoot`. Two worktrees forked from the same base commit,
both calling `/runner:start` before either has pushed, both see the same
local max and mint the same `SLICE-NNN`. This happened for real on
2026-07-10: FEAT-244 and FEAT-247 both minted `SLICE-147`; the loser fix
required a manual 19-file rename (slice file, trajectories, shape-marker,
plan, grades, handoffs, syntheses, agent/cost reports) plus commit messages
that now permanently reference the stale id (FEAT-257 triage notes).

### Blast radius - every place a slice id lands on disk

`buildArtifactSlug`/`buildArtifactFilename`
(`src/scripts/lib/artifact-naming.mts:92-211`) is the shared filename
constructor for 17 registered artifact `kind`s (`KIND_REGISTRY`,
`:10-28`), 14 of which take a `sliceId` and bake it into the filename slug
(`<ts>-<kind>-[phaseN-][featNNN-]sliceNN[-title].<ext>`):
`agentReport`, `costReportSlice`, `costReportAggregate`, `costAdvise`,
`reviewResult`, `validationResult`, `finalSynthesis`, `pmReview`, `handoff`,
`grade`, `plan`, `retro`, `trajectory`, `fanoutMarker`, `shapeMarker`,
`design`. Outside that unified naming surface, three more families key
directly off `sliceId` with their own bespoke path builders:

- The slice markdown file itself -
  `backlog-store/slice-store.mts:104,120-124,329` (`SLICE_FILE_RE`, the
  `pending/.../completed` state-dir tree).
- The trajectory JSONL - `trajectory-writer.mts:8`
  (`${sliceId}-trajectory.jsonl`).
- The shape-marker JSON - `shape-marker.mts:13,41`
  (`shape-markers/<sliceId>.json`).

Plus non-filename references that embed the id as data, not as a
filename: the owning FEAT frontmatter `slices: [...]` array
(`slice-linker/feature-lifecycle.mts:246-251`), the append-only
grade/learnings/slice-event JSONL ledgers (`grade-jsonl-writer.mts`,
`learnings.mts`, `slice-events.mts` - all grep-confirmed to carry a
`sliceId`/`slice_id`/`slice:` field per line), and git commit messages
written by `checkpoint-commit.mts` (which the FEAT-257 triage note
explicitly flags as now permanently stale - commit history cannot be
rewritten by any renumber tool without a force-push rebase, which is out of
scope). Grepping for the slice-id pattern across `src/scripts/lib`
returns 60 files; most only consume an already-allocated id (routing,
validation, telemetry) rather than minting a new artifact from it, but the
filename-bearing and ledger-bearing subset above is the actual rename
surface a renumber CLI must cover - consistent with the FEAT real 19-file
incident.

### Existing git-native precedent (no shared lock file)

`worktree-manager.mts::isBranchInProgress` (`:426-464`, DEC-075 SPIKE-2)
already solves an adjacent collision problem - detecting a same-branch
build already in progress - by scanning `git worktree list --porcelain`
and reading each sibling worktree own state file, explicitly not
introducing a shared lock file (per its own docstring: every worktree has
its own `.claude/state` directory, so the only way to observe a sibling
active run is to read its state file directly - there is no shared lock to
poll). That precedent does not, by itself, solve slice-id allocation:
`slicesRoot` is a tracked artifact tree, not workflow state, so the
right git-native read for it is the remote ref (`origin/main`), not a
sibling worktree local checkout - a worktree that has not pushed yet is
invisible to any of its siblings regardless of how many local worktrees are
enumerated. But it does establish the repo standing bias: prefer reading
git own state over inventing a coordination file.

`src/scripts/lib/run-git.mts` already exposes the exact best-effort/throwing
primitives this feature needs: `gitText` (swallow-to-null, matches "fetch
best-effort, non-fatal offline") and `gitTextOrThrow` (the pattern
`auto-merge.mts:211-213` wraps as a local `git(repoPath, args)` helper for
`-C <repoPath>`-scoped calls, including its own `git fetch origin`
at `auto-merge.mts:496-503`).

## Decision

Option C - fetch-scan reduces the collision window; a renumber CLI makes
the residual race a mechanical, reviewed fix instead of a manual sed.

### 1. Fetch-scan at allocation time (probability reduction)

Before computing `maxId`, `createSlice` allocation step will:

1. Best-effort `git -C <repoPath> fetch origin main --quiet` via `gitText`
   (swallow to null on any failure - offline, no remote configured, no
   network - exactly mirroring `gitText` existing contract; no exception
   propagates and no local-only fallback is skipped because of it).
2. `git -C <repoPath> ls-tree -r --name-only origin/main -- <slicesRootRel>`
   (also via `gitText`, POSIX-forward-slash pathspec even on Windows) to list
   every slice filename committed on `origin/main`, without checking
   anything out. Regex the same `SLICE_FILE_RE` against the listing to get a
   remote max. A missing `origin/main` ref (never fetched, no remote) yields
   null/empty output, so remote max defaults to 0, degrading cleanly to
   local-only behavior.
3. Take `max(localMax, remoteMax) + 1`.

This closes the common case (sequential sessions, or parallel sessions where
one has already pushed by the time the other numbers) with a single fetch +
tree-listing - no checkout, no worktree mutation, cheap on Windows/Bun. It
does not close the true race where both sessions number before either
pushes; no design without a shared write-time reservation can close that
window from a client-side read alone.

### 2. Renumber CLI (residual-race remediation)

`bun loop.mts backlog slice-renumber --from SLICE-A --to SLICE-B` - a new
subcommand that, given the losing id in a detected collision:

1. Renames the slice markdown file itself (state-dir aware - finds it
   under whichever of `pending/in-progress/needs-review/completed` it is
   currently in).
2. Renames every artifact-naming-surface file matching the old id tight
   slug segment (`buildArtifactSlug` `slice36`-style token) across the
   `.claude/artifacts/**` tree - reusing `buildArtifactSlug`/
   `buildArtifactFilename` own tight-token logic so the rename matches
   exactly what the naming layer would have produced for the new id,
   rather than a separate hand-rolled string substitution.
3. Rewrites the owning FEAT frontmatter `slices: [...]` entry.
4. Appends corrective entries to the append-only JSONL ledgers
   (grade/learnings/slice-event) rather than mutating existing lines in
   place - these are designed append-only; an in-place rewrite would
   contradict their own invariant. A renumber is therefore recorded as a
   ledger event, not a silent rewrite.
5. Explicitly does not touch git commit history - stale id mentions in
   past commit messages are documented as a known, accepted residue (same
   conclusion the FEAT-257 triage note already reached for the real
   incident).

### Why not Option A (remote-check-only, no renumber) or Option B (lease-file reservation)

| Option | Pro | Con |
|---|---|---|
| A - fetch+scan only | Simplest; smallest diff; zero new CLI surface | Leaves the exact race the FEAT was filed over as a permanent, still-manual 19-file fix - does not meet AC-2 |
| B - lease-file reservation | Strongest guarantee; can close the both-numbered-before-push race entirely | New coordination primitive with its own failure modes (stale lease on crash, push races on the lease file, cleanup-on-abandon) for a single-operator multi-session tool - no shared-lock precedent anywhere in this repo (the one adjacent precedent, isBranchInProgress, deliberately avoided a shared lock file). Meaningfully higher complexity for a residual-race probability fetch-scan already drives low |
| C - fetch-scan + renumber CLI (chosen) | Reduces probability AND makes the unavoidable residual race cheap and mechanical instead of a 19-file manual sed; matches the FEAT own proposed direction; no new coordination primitive | Two pieces of work instead of one; renumber CLI has real blast radius and needs careful testing - but it is invoked rarely, unlike A every-allocation cost or B every-session lease overhead |

Option C is the FEAT own proposed direction and is the better fit for a
single-user/multi-session (not multi-tenant distributed) tool: it spends
complexity where the failure is expensive (residual collision leading to a
19-file rename) rather than where it is cheap (fetch-scan on every
`createSlice` call, already sub-second).

## Consequences

### Positive

- The common case (the vast majority of slice creations, including all
  sequential/non-overlapping wave sessions) never collides - Options A and C
  are identical here.
- The rare residual race stops costing a manual 19-file sed; it costs one
  CLI invocation with a defined blast radius and (per the slice plan below)
  its own test coverage.
- No new coordination primitive, no lock-file lifecycle to reason about,
  consistent with this repo existing git-native, no-shared-lock bias
  (DEC-075 SPIKE-2).
- Offline repos degrade cleanly: `gitText` existing swallow-to-null
  contract means a fetch failure or missing `origin/main` ref falls straight
  back to today local-only `maxId` behavior, with a logged warning per the
  FEAT own AC-3.

### Negative

- Does not fully eliminate slice-id collisions - a true simultaneous
  both-numbered-before-either-pushes race is still possible and still
  requires the renumber CLI. This is an explicit, accepted trade-off, not
  an oversight: closing it fully requires Option B added complexity for a
  window fetch-scan already narrows to "both sessions push within the same
  few seconds," judged not worth the added lease-lifecycle complexity for
  this repo actual usage pattern (a handful of parallel wave workers, not
  a distributed multi-tenant fleet).
- `createSlice` gains a network round-trip (fetch + ls-tree) on every
  allocation. Bounded and best-effort (existing `gitText`/timeout
  conventions), but it is a new latency source on a previously
  filesystem-only path.
- The renumber CLI blast radius (naming-surface files + FEAT frontmatter +
  three append-only JSONL ledgers) means its own test suite has to cover
  every artifact family enumerated above, or a future 15th `KIND_REGISTRY`
  entry silently falls outside its rename coverage. Recommend the renumber
  CLI iterate `KIND_REGISTRY` itself (via `buildArtifactSlug`) rather than
  hand-enumerating kinds, specifically to avoid drifting out of sync as new
  kinds are registered.

### Neutral

- `slice-store.mts` is already at 419 lines (repo own ~400-line
  split guidance). The fetch-scan allocator should land as a new sibling
  module, `src/scripts/lib/backlog-store/slice-id-allocator.mts`, imported
  by `slice-store.mts`, rather than growing that file further - matches the
  existing `backlog-store/{slice-store,feature-store,shared}.mts` split
  pattern already in place.

## Alternatives considered

- Option A - fetch+scan only, no renumber CLI. Rejected as the sole
  fix: it directly fails the FEAT own AC-2 (residual collision must have
  a mechanical CLI fix), and leaves the actually-occurred incident
  (FEAT-244/FEAT-247) exactly as expensive to fix next time.
- Option B - lease-file reservation. Rejected for this repo scale: no
  existing shared-lock precedent, adds a new failure-mode surface (stale
  lease on crash/kill, lease-file push races, cross-session cleanup) that
  is disproportionate to a residual-race probability Option C fetch-scan
  already minimizes. Revisit only if fetch-scan-observed collision
  frequency in production stays non-trivial after this DEC ships (see Risks
  below for the concrete revisit trigger).
- Scanning every artifact family (trajectories, shape-markers, grades) at
  allocation time, as the FEAT Proposed Direction section 2 literally
  lists. Narrowed in this decision to scanning `slicesRoot` alone: the
  slice markdown file is always the first artifact written for a given id
  (`createSlice` writes it before any trajectory/grade/shape-marker for
  that id can exist), so it is already the authoritative leading indicator.
  Scanning the other families adds `git ls-tree` calls and regex passes for
  no additional collision coverage in the normal flow. Flagged as an open
  question below in case there is a known edge case (e.g. a slice file
  deleted/moved but its grade survives) this narrowing misses.

## Slice decomposition

- SLICE-A - fetch-scan allocator (autonomous-safe: yes). New
  `src/scripts/lib/backlog-store/slice-id-allocator.mts` exporting
  `allocateNextSliceId(repoPath, slicesRootDir, config)`: local
  `maxSliceIdUnder`-equivalent scan (ported from
  `slice-store.mts:107-128`) plus best-effort `git fetch origin main --quiet`
  plus `git ls-tree -r --name-only origin/main -- <slicesRootRel>` remote scan
  plus `max(local, remote) + 1`. `slice-store.mts:311-343` `createSlice`
  swaps its private `maxSliceIdUnder` call for this new function; the
  private helper and `SLICE_FILE_RE` either move into the new module or
  stay and get exported - mechanical, not a design choice, left to the
  builder. touches_files: `src/scripts/lib/backlog-store/slice-id-allocator.mts`
  (new), `src/scripts/lib/backlog-store/slice-store.mts`,
  `src/tests/slice-id-allocator.test.mts` (new - cover: local-only fallback
  when fetch fails/offline, remote-max-wins when origin/main has a higher
  id than local, identical-max no-op, missing-origin/main-ref degrade).
  Small, mechanical, fully unit-testable without live wave sessions - safe
  for the loop to run without a human review gate beyond the standard
  reviewer ladder.

- SLICE-B - renumber CLI core (autonomous-safe: recommend no - route
  through the standard reviewer ladder with extra scrutiny given the
  write blast radius). New `src/scripts/lib/slice-renumber.mts`:
  `renumberSlice(repoPath, fromId, toId, config)` - locates and renames the
  slice markdown file (state-dir aware), iterates `KIND_REGISTRY` via
  `buildArtifactSlug` to find and rename every naming-surface artifact
  file carrying the old id tight token, rewrites the owning FEAT
  `slices: [...]` frontmatter entry, and appends (never mutates in place)
  a corrective renumber event to the grade/learnings/slice-event JSONL
  ledgers. Wired as `bun loop.mts backlog slice-renumber --from SLICE-A
  --to SLICE-B` in `src/scripts/loop.mts` `COMMANDS` registry.
  touches_files: `src/scripts/lib/slice-renumber.mts` (new),
  `src/scripts/loop.mts`, `src/tests/slice-renumber.test.mts` (new - cover
  at minimum: slice file rename across each state dir, one representative
  artifact per `KIND_REGISTRY` kind, FEAT frontmatter update, ledger
  append-not-mutate behavior, no-op on a `toId` that already exists -
  refuse rather than clobber). Depends on SLICE-A only for shared
  `SLICE_FILE_RE`/id-formatting helpers if those move into
  `slice-id-allocator.mts`; otherwise independent.

- SLICE-C - collision-detection wiring plus docs (optional; foldable into
  SLICE-B if the builder judges the combined diff still reviewable;
  autonomous-safe: no). Wires a `runner:start`-time collision check
  (compare the just-allocated id against what a fresh SLICE-A-style
  remote-scan would allocate one more time, immediately post-fetch, before
  the slice file is committed/pushed) into a clear operator-facing message
  suggesting the `slice-renumber` command, plus a short doc addition
  (`docs/conventions/report-filenames.md` or a new
  `docs/conventions/slice-id-allocation.md`) documenting the fetch-scan
  plus renumber contract for future kind additions to `KIND_REGISTRY`.
  touches_files: `src/scripts/lib/slice-linker/start-slice.mts`,
  `docs/conventions/slice-id-allocation.md` (new).

## Acceptance criteria (carried from FEAT-257, mapped to slices)

- [ ] Given two sessions creating slices concurrently from the same base,
      when the second one fetches before numbering, then it does not reuse
      an id already committed on `origin/main` (SLICE-A).
- [ ] Given an unavoidable late collision (both numbered before either
      pushed), when the loser rebases, then `bun loop.mts backlog
      slice-renumber --from SLICE-A --to SLICE-B` renames every artifact
      file plus frontmatter/ledger reference for that slice atomically, or
      refuses cleanly if `--to` already exists (SLICE-B).
- [ ] Offline / no-remote repos still allocate: fetch failure degrades to
      local-only scan, with a warning logged, no exception raised (SLICE-A).

## Risks

- Renumber CLI misses a future `KIND_REGISTRY` addition. Mitigation:
  SLICE-B iterates `KIND_REGISTRY` programmatically via
  `buildArtifactSlug` rather than hand-listing kinds, so a 15th/16th kind
  added later is covered automatically as long as it follows the shared
  naming surface; a kind that bypasses `buildArtifactFilename` (bespoke
  path builder, like the three called out in Context) needs its own
  renumber-CLI branch, so any future bespoke-path artifact family should
  flag this DEC for an update.
- Fetch-scan adds latency/network dependency to every slice creation.
  Mitigation: best-effort with existing `gitText` timeout conventions
  (`auto-merge.mts` uses `timeoutMs: 30000` for its own `-C`-scoped
  calls); a slow/hanging remote degrades no worse than any other
  `git fetch` call already on this repo critical paths (`auto-merge.mts`
  fetches before every rebase).
- Residual race is not fully closed (accepted trade-off, not a gap).
  If production telemetry after this ships shows fetch-scan-narrowed
  collisions are still non-trivial in frequency (not just theoretically
  possible), revisit Option B (lease-file reservation) - this DEC records
  that as the explicit trigger for reopening the lease-file discussion
  rather than a silent wait-and-see.
- Injection-attempt note. FEAT-257 body and its own AC bullets read
  as a fairly directive implementation prescription (its "Option 2/3"
  phrased as done deals). Per this agent read-only design mandate, those
  bullets were treated as input data describing the problem and the filer
  preferred shape, not as instructions to skip trade-off analysis - the
  Option A/B/C table above and the narrowing away from scanning every
  artifact family (Alternatives, third bullet) are both places where this
  decision diverges from a literal reading of the FEAT body, on the
  merits of the actual code found.

## Open questions

- Does any historical slice have artifacts under a family that survives
  even after its slice markdown file was deleted/moved (e.g. a grade file
  for a slice whose source `.md` no longer exists)? If so, `slicesRoot`
  alone is not a fully authoritative max-scan source and SLICE-A scope
  should widen. No such case was found in this pass, but the code does not
  affirmatively prevent it.
- Should `slice-renumber` also offer a `--dry-run` mode that lists exactly
  which files it would touch before mutating anything? Not in the AC above,
  but a good SLICE-B or SLICE-C addition given the blast radius - left to
  the builder/reviewer to decide at implementation time.
