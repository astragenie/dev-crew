# DEC-065: Memory-sink is opt-in, project-from-config, code-enforced

## Context

FEAT-216 added a prompt-level astramem mirror in `commands/close.md` (the
closing agent was told to call the astramem `remember` tool per new decision).
The operator asked to generalize it into a real feature that fires on every
decision made / lesson learned, gated on whether memory is enabled. Three
design points needed ratifying before wiring it into the widely-used
grade-write and learnings paths.

## Decision

1. **Opt-in enablement.** `memory-sink.mts` reads `memory.enabled` from
   `.claude/loop.json`. An absent `memory` block (or unknown value) is treated
   as **OFF**, not auto. Only `on`/`always`/`true`, or `auto` (fire when the
   astramem CLI resolves), enable it. Rationale: the sink is wired into
   `grade-writer.mts` and `learnings.mts`, which have hundreds of test
   temp-repos with no memory config — an auto default would spawn the real
   astramem CLI on developer machines during the test suite. Opt-in keeps
   unconfigured repos (and all tests) silent, and matches the operator's
   "check if memory isEnabled" framing.

2. **Project id from customer config, never hardcoded.** The cortex project id
   is `memory.project` (explicit override) else the repo's `productName`. No
   `"loop"`-style literal. Decisions/lessons also embed `[FEAT-x/SLICE-y]`
   trace tags in the content for cross-repo/slice traceability (the astramem
   `remember` CLI ignores unknown flags, so ids ride in `--content`).

3. **Code-enforced, not an agent step.** The mirror runs in
   `grade-writer.mts::extractDecisions` (per new `DEC-NNN`) and
   `learnings.mts::logLearning` (per learning) via `memory-sink` — reusing the
   `memory-bridge.mts::resolveCli` + fail-silent, 2s-capped spawn pattern. This
   supersedes the FEAT-216 prompt-level instruction in `commands/close.md`
   (which is updated to say the mirror is automatic, to avoid a double-write).
   Manual ADRs authored outside a close/learn flow remain the only case a human
   still mirrors by hand.

## Consequences

### Positive

- Every decision/lesson is durably mirrored when memory is enabled, with no
  reliance on an agent remembering to do it.
- No test pollution / no behavior change for repos that never opt in.
- Traceable by product + FEAT + SLICE.

### Negative

- Opt-in means a repo that wants mirroring must add `memory.enabled` to
  `loop.json` (done for this repo: `"auto"`).
- Two stores (repo DEC files + astramem) still exist; the sink keeps them in
  sync forward-only (no back-fill of pre-FEAT-217 decisions).

### Security

- Content and the `--project` argv are sanitized (control chars stripped,
  capped); `spawn` uses an args array (no shell) so config-sourced text cannot
  inject commands. No secret/token is ever passed as content.
