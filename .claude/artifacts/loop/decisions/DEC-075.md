# DEC-075: Bounded reject-to-defer loop for the pre-slice-1 architect gate (never block for a human)

## Amendment (2026-07-09, same day)

The original text of this ADR (below) flagged `arch_review`/`arch_risk`
as named-but-unimplemented fields — the preflight instruction told the
loop the persist call "records arch_review/arch_risk" while
`applyArchGateVerdict` silently didn't. That gap is now closed:
`applyArchGateVerdict` writes `arch_review` (the normalized verdict,
`approved`/`rejected`) and `arch_risk` (a risk-flag string array —
`riskFlags` when supplied, else falling back to `objections`) on every
non-no-op verdict call, and `backlog arch-gate-apply` gained a sibling
`--risk-flags <file.json>` flag alongside `--objections`. Sole writer
remains `applyArchGateVerdict` — no second writer was introduced. See
`src/scripts/lib/arch-gate.mts` (`ApplyArchGateVerdictOpts.riskFlags`)
and the CLAUDE.md ARCHITECT GATE frontmatter section for the current
field contract. The two callouts below that described this as an open
gap are corrected in place rather than left contradictory.

## Context

P0/P1 fullstack FEATs previously went straight from PM triage to slice-1
builder dispatch with no independent architecture review. A bad service
boundary or missed integration risk on a fullstack FEAT was only caught
after code existed, when the fix is expensive. The autonomous loop also
cannot pause and wait for a human reviewer mid-run — `loop.marathonMode`
walks the whole backlog unattended, so any gate added ahead of slice 1
has to resolve itself (approve or defer) without a synchronous human in
the loop.

The gate was built directly on `feat/arch-gate-*` branches (WS-3 builder
variants, PM `--rescope`, WS-4 worktree collision detection) and merged
into `feat/arch-gate-integration` at commit `68a931a4` ("pre-slice-1
architect + risk gate with bounded reject→defer loop"). No FEAT/SLICE
record was filed for this workstream in the backlog — hence
`introduced_by_slice: n/a` above; the implementation commit is the
authoritative record.

## Decision

We will run a pre-slice-1 **ARCHITECT GATE** for P0/P1 fullstack FEATs
that: (1) dispatches `crew:architect-feature` to produce a contracts
artifact, (2) dispatches `crew:architect-reviewer` to assess it and
return a verdict, (3) persists that verdict into FEAT frontmatter as a
bounded reject-loop state machine, and (4) after a fixed number of
rejected rounds, **defers the FEAT rather than escalating to or blocking
on a human**. The gate never synchronously blocks the autonomous loop.

### Gate condition (`shouldRunArchGate`, `src/scripts/lib/arch-gate.mts`)

The gate fires only when ALL of: crew is available, this is the FEAT's
first slice (`feature.slices[0]`), the FEAT's effective priority
(`pm_composite_priority` else `priority`) is `P0` or `P1`, and the WS-3
builder variant is a positive dual-surface signal (`fullstack` or
`parallel-fe-be` — not `frontend`/`backend`/`unknown`).

### Reject flow

1. `crew:architect-reviewer` returns a verdict: `approved` /
   `approved_with_notes` (normalizes to `approved`) or `rejected` /
   `needs_revision` (normalizes to `rejected`) — `normalizeVerdict()`
   throws on any other string rather than silently guessing.
2. The orchestrating loop persists the verdict via
   `bun loop.mts backlog arch-gate-apply --id <FEAT> --verdict <v>
   [--objections <file>] [--spent-usd <n>]`, the sole CLI caller of
   `applyArchGateVerdict`.
3. On `rejected`, with attempts remaining, `arch_status` becomes
   `gate_in_progress` and the loop dispatches `bun loop.mts backlog
   pm-rescope --file <p> --ids <FEAT>` with the reviewer's objections,
   then re-runs `/runner:start` for the FEAT to re-enter the gate.
4. On `rejected` with attempts exhausted, the FEAT is auto-deferred (see
   Guard/budget details below) — the loop moves on to the next backlog
   item without retrying this FEAT again this session.

### The 3 guards

1. **Persisted `arch_attempt` counter.** A rejection increments
   `arch_attempt` in FEAT frontmatter (`computeArchGateTransition`); the
   1st rejection sets `attempt = 1` and retries (`1 < MAX_ARCH_GATE_ATTEMPTS`),
   the 2nd sets `attempt = 2` and defers (`2` is not `< 2`,
   `MAX_ARCH_GATE_ATTEMPTS = 2`). Because this is read back off disk via
   `findFeatureById` on every `runner:start` / `arch-gate-apply` call,
   it survives process restarts and re-triage passes — including a
   `pm-apply --include-triaged` run over the same FEAT — because the
   read-guard (Guard 3) skips the write path entirely while the gate is
   active, so nothing ever resets or bypasses the counter out from under
   the state machine.
2. **`gate_in_progress` re-entry lock.** `arch_status` is the tri-state
   flag (`gate_in_progress | approved | deferred_design`) that
   `shouldRunArchGate` reads to decide re-entry behavior: `deferred_design`
   never re-enters; `approved` is already resolved (skip); `gate_in_progress`
   force re-fires the gate on the next `runner:start` call **regardless of
   contracts-artifact-file state** — this is the piece that lets a rescoped
   FEAT re-enter round 2 even though `crew:architect-feature` regenerates
   the same contracts path every round (so "file already exists" cannot be
   used to distinguish round 1 from round 2). Absent any `arch_status`,
   first entry is instead gated on `contractsArtifactExists()` — the
   contracts file itself is the entry signal for a FEAT that has never
   been through the gate.
3. **`pm-apply` read-guard.** `isArchGateActive()`
   (`src/scripts/lib/pm-apply.mts`) checks `arch_status` against
   `GATE_ACTIVE_ARCH_STATUSES = {"deferred_design", "gate_in_progress"}`
   before `applyPmResults` writes a priority/promotion update for a FEAT.
   A match skips `commitEntry` for that FEAT entirely (reported back as
   `gated`, not a failure — `pm-apply`'s exit code is unaffected) so a
   routine PM re-triage pass — including one invoked with
   `--include-triaged` — can never re-promote or re-prioritize a FEAT
   the gate has already deferred or is mid-cycle on. This guard is
   read-only: it never writes `arch_*` fields itself (`arch-gate.mts`'s
   `applyArchGateVerdict` is the sole writer), and it is deliberately
   **not** applied to `applyPmRescope` — a rescope write during
   `gate_in_progress` is the expected write the gate itself asked for;
   gating that path would deadlock the reject loop.

### Priority step-down on defer

When attempts are exhausted, `demotePriority()` steps the FEAT's
priority down one tier (`P0 → P1 → P2`, floored at `P2`), and
`applyArchGateVerdict` additionally sets `autonomous_safe: false` and
`arch_defer_reason` (joined reviewer objections, or a fallback string
when none were supplied) in the same frontmatter write as the
`arch_status: "deferred_design"` transition.

### Budget

`archGateBudgetUsdPerFeat` in `.claude/loop.json` configures a soft
per-FEAT ceiling, default **$100** (`DEFAULT_ARCH_GATE_BUDGET_USD`),
clamped to a hard ceiling of **$160** (`ARCH_GATE_BUDGET_HARD_CEILING_USD`)
regardless of what the operator configures. `checkArchGateBudget` runs
BEFORE any frontmatter write; if `actualUsdSpent` (summed from
`.claude/artifacts/crew/cost/*-cost-report-*.md` reports tagged
`feature: <id>`) exceeds the resolved ceiling, it throws
`ArchGateBudgetExceededError` (`halt_reason: "budget_exceeded"`) and
**nothing is written** — this is a **halt-and-escalate to the operator**,
not a silent defer. `runBacklogArchGateApply` (`loop.mts`) sets
`process.exitCode = 1` and returns `{ halted: true, halt_reason:
"budget_exceeded", ... }` on this path; the dispatch instruction tells
the orchestrating loop to STOP and surface it rather than proceeding.

### Decision basis: categorical, not numeric

The gate's approve/reject decision is driven entirely by the
architect-reviewer's **categorical verdict** string
(`approved|approved_with_notes|rejected|needs_revision`,
`normalizeVerdict`). There is no numeric `arch_risk` score or threshold
anywhere in `arch-gate.mts` or the `arch-gate-apply` CLI path today — a
numeric risk threshold (e.g. "defer automatically above risk 0.7") is
explicitly **deferred as future work**, not implemented. `arch_risk` IS
now a persisted field (see Amendment below) — it is a recorded list of
risk-flag strings, not a numeric score, so this categorical-vs-numeric
distinction is unaffected by that gap-close.

## Consequences

### Positive

- P0/P1 fullstack FEATs get an independent architecture review before
  any code is written, without adding a synchronous human checkpoint to
  the autonomous loop — `loop.marathonMode` can keep walking the backlog.
- The reject loop is bounded and self-terminating: at most 2 rejected
  rounds before the FEAT steps down in priority and is marked
  `autonomous_safe: false`, so a persistently-rejected design cannot
  loop the same FEAT forever or silently ship an un-reviewed design.
- Re-entry is driven by a frontmatter state machine, not an in-process
  loop or in-memory retry count — the cycle survives process restarts,
  worktree switches, and re-triage passes (including `--include-triaged`)
  cleanly, because Guards 1–3 are all disk-backed and mutually
  consistent (single writer: `applyArchGateVerdict`).
- Budget overrun is a hard, visible halt rather than a silently-deferred
  FEAT — an operator is never left wondering why a FEAT got demoted when
  the real cause was runaway architect-review spend.

### Negative

- A FEAT that is demoted to `deferred_design` still requires a human (or
  a future FEAT) to look at `arch_defer_reason` and decide whether to
  manually re-open the gate (there is no automatic re-entry once
  `deferred_design` is set — `shouldRunArchGate` refuses unconditionally).
- The categorical-only decision basis (no numeric `arch_risk` threshold)
  means there is currently no way to configure "defer immediately on
  high risk, skip the rescope round" — every rejection gets exactly one
  rescope attempt regardless of how severe the reviewer's objections are.
- `readFeatureCostSpendUsd`'s per-FEAT cost sum is an approximation: any
  cost report tagged `feature: <id>` counts toward the budget, not only
  reports from `architect-feature`/`architect-reviewer` dispatches
  specifically — documented as a known limitation in the function's
  docstring, not silently assumed exact.

### Neutral

- The gate is a soft-skip, not a hard dependency: `maybeBuildArchGatePreflight`
  logs a warning and proceeds without the gate if the `crew` CLI isn't
  discoverable in the plugin cache, rather than failing the slice-build
  dispatch outright.

## Alternatives considered

- **Option A — bounded reject loop, then defer (chosen).** Caps rejected
  rounds at `MAX_ARCH_GATE_ATTEMPTS = 2`, then demotes priority and marks
  `autonomous_safe: false` rather than escalating to a human. Keeps the
  autonomous loop moving through the backlog while still capping how
  much rework a single contested design can absorb.
- **Option B — one-pass: escalate and stop on any rejection.** Run the
  gate once; on the first `rejected` verdict, halt the loop and require
  an operator to resolve it before any further backlog progress.
  Rejected: a single reviewer objection is often addressable by a
  `pm-rescope` pass without human intervention (missing an edge case in
  the AC, an underspecified boundary) — escalating immediately would
  turn routine, fixable review feedback into a hard stop on every
  `marathonMode` run touching a P0/P1 fullstack FEAT, defeating the
  point of an unattended loop.
- **Option C — unbounded/in-memory retry with silent demote.** Keep
  looping `architect-feature` → `architect-reviewer` → rescope in
  process memory until approved, then silently drop priority if it never
  converges, with no persisted attempt counter. Rejected on two grounds:
  (1) an in-memory retry count is lost on process restart, worktree
  switch, or crash — the loop could re-run the full cycle from attempt 0
  indefinitely (thrash), and (2) a silent demote gives the operator no
  visible reason (`arch_defer_reason`) and no cost ceiling — an
  adversarial or persistently-underspecified FEAT could burn unbounded
  architect-review spend before anyone noticed. The chosen design's
  disk-persisted counter plus the hard budget ceiling (Budget section
  above) closes both gaps.
