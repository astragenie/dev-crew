## Decisions

### DEC-004: Pending-dispatch marker file is the cross-process spawn primitive

**Rationale**: No existing pattern in `loop` plugin for spawning a sub-agent from inside a Node CLI command (the existing `crew-bridge.mts` is invoked from within a dispatched agent, not the reverse). The simplest correct primitive is a marker file (`pending-dispatch.json`) that an outer harness consumes. SLICE-B/C/D will define the harness consumer + cleanup contract. Alternative considered: shell out to `claude` CLI with `--agent` flag — rejected because it couples the plugin to a specific CLI invocation shape and breaks under arbitrary host environments.

**Consequences**:
- positive: dispatch is a pure file write — testable, idempotent, no process lifecycle to manage in SLICE-A
- positive: SLICE-D can implement async consumption + cleanup without rewriting SLICE-A
- negative: marker files accumulate until SLICE-D ships consumer + cleanup (reviewer flagged)
- negative: feedback loop from spawned agent back to caller is deferred (no streaming output to parent CLI)

### DEC-005: appendAuditLog failure propagates to caller (does not swallow)

**Rationale**: Matches the existing `crew-bridge.mts` audit pattern in this repo. Silent swallow of disk-full or permission errors would lose the audit signal that something is wrong with the loop's own bookkeeping — exactly the signal we want to surface, not hide. Caller may choose to wrap in try/catch if they have a fallback; library does not impose that policy.

**Consequences**:
- positive: disk-full / permission errors surface immediately rather than corrupting silent state
- positive: consistent with existing repo idiom — future maintainers don't have to learn two error patterns
- negative: if a caller forgets to wrap, an audit-log write failure could abort a CLI command. Mitigation: documented in module header and reviewer-flagged for SLICE-B/C/D wiring sites.
