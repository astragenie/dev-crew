## Lessons

- A deliberately-red test needs its red state documented where a CI reader looks, not only in the FEAT body: the verifier found gate 41 red with nothing in docs/ci-gates.md or docs/memory.md explaining it. A designed-red gate without a paper trail reads as a broken branch.
- Deriving the CLI entry list by scraping `bun "${CLAUDE_PLUGIN_ROOT}/..."` out of commands/ and agents/ makes the test track the future dist/ path rewrite for free, and it surfaced that `show-workflow-state` is invoked nowhere in the shipped command surface (build.md reads workflow-state.json via jq instead).
- Test helpers that stage a full repo copy must own their teardown from the first commit: two stagings per run at ~269 MB on a persistent self-hosted runner, with the test red indefinitely, is an unbounded disk leak that no assertion catches.

## Decisions

### DEC-044: Consumer-install smoke test is a ratchet, not a quarantine: gate 41 stays red until FEAT-026

**Rationale**: The shipped plugin crashes for consumers because the cache has no node_modules (audit #41). The test runs every shipped hook and CLI entry from a node_modules-free staged copy and records the 49 currently-crashing entries in EXPECTED_FAIL. Keeping it un-quarantined and red is the point: the same ratchet fails when a listed entry starts passing (remove it) or an unlisted one breaks (newly broken).

**Consequences**:
- Gate 41 and CI's slow-tests are expected red on fix/audit-2026-11 until FEAT-026 ships dist/ bundles; the merge-blocking gate job depends only on fast-gate, so merges are unaffected. Documented in docs/ci-gates.md gate 41 and docs/memory.md CI gates.
