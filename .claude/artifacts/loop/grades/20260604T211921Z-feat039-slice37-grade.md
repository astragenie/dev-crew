## Lessons

- Sonnet-only slice at $18.36 vs SLICE-36 Opus at $85.97 — 79% cost reduction with no quality loss (695/695 pass, all 6 ACs met). Model routing policy change pays for itself immediately.
- ESLint complexity cap 15 forced good design: `buildCeilingSnapshotEntry` and `gatherStopInputs` helpers emerged from the constraint rather than from upfront design. The cap works.
- `tsconfig.test.json` (noImplicitAny:false) masks type errors in test files at IDE level; only `npm run typecheck` is authoritative. IDE red-squiggle false alarms are a recurring trap.
- read-guard hook operates on tool events, not file state — it cannot retroactively catch re-reads that happened during its own authoring slice. Expected; not a defect.
- Bash hooks on Windows depend on Git Bash / WSL in PATH. Not validated this slice. Low risk for CI (Linux) but worth noting for Windows-first install paths.

## Decisions

### DEC-008: Model routing policy — sonnet for review/build/validate, opus for sliceStart/gradeWrite

**Rationale**: Audit of 10 routing sites showed review and build phases do not need frontier reasoning; sonnet delivers equivalent quality. sliceStart and gradeWrite involve architectural judgment and retrospective synthesis where opus is worth the cost premium.

**Consequences**:
- Review and build costs drop ~4× per slice
- Complex review edge cases (subtle concurrency bugs, novel abstractions) may receive less deep scrutiny — revert per-slice when warranted per ADR
- ADR at `docs/decisions/DEC-008-model-routing-policy.md`

## Surprises

- 17 re-reads still flagged in SLICE-37's own cost report despite the hook being the slice's output — expected (hook guards future sessions, not its own authoring run), but worth stating explicitly so future graders don't interpret it as the feature failing.
- FEAT-039 fully done in one slice (scoped correctly to this-repo items only). Items 1 and 5 (crew plugin smarter detector, brief-me fix) cleanly deferred without scope creep.

## Followups

- Smarter re-read detector in crew plugin: separate `postEditReReadCount` / `sameRangeReReadCount` / `pagingReadCount` counters (FEAT-039 item 1 — crew plugin repo, not this repo).
- brief-me: re-read count display should distinguish post-edit vs paging vs genuine re-read (FEAT-039 item 5 — also crew plugin).
- Validate read-guard.sh on a Windows-native PATH (no WSL) — low risk since CI runs Linux, but a Windows install guide note would be clean.

## What went well

All 6 ACs shipped clean in a single slice with 695/695 tests passing. The model routing switch from opus to sonnet for review/build/validate worked without any quality regression — the reviewer APPROVED with zero required changes. Complexity discipline (ESLint cap 15) drove good extraction: `buildCeilingSnapshotEntry` and `gatherStopInputs` are cleaner than the inline version would have been. Scope discipline held: deferred crew-plugin items without pulling them in.

## What went wrong

17 re-reads flagged in the slice's own cost report felt alarming until it was understood that the hook can only guard future runs. The cost-to-explain ratio of this confusion is high — the final synthesis should have called it out explicitly. It didn't.

## What I would do differently next time

Open the tsconfig.test.json config explicitly in the research phase of any slice that adds new test files, so the IDE false-alarm pattern is already defused before implementation starts rather than discovered during lint/typecheck runs.
