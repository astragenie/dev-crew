## Lessons

- Factory function pattern (`getProvider`) is cleaner than a class registry — no static state, easy to test, easy to extend with a new case.
- `requires_validation: false` on pure library slices with full test coverage is the right call. Test suite IS the validation for adapter-layer code.
- Pre-declaring 3 slices for FEAT-024 (A/B/C) paid off: SLICE-14 had zero scope creep because the boundaries were explicit from the start.

## Decisions

### DEC-002: getProvider falls back to NoopProvider for unknown provider names without warning

**Rationale**: Unknown config keys at startup should not crash ceremony hooks mid-run. A silent no-op is safer than a throw. The alternative (warn + noop) was considered but adds noise for users who intentionally leave provider unconfigured.

**Consequences**:
- Positive: misconfigured repos don't break on loop start
- Negative: typos in `taskStore.provider` (e.g. "gitHub") produce silent no-ops, hard to debug without reading docs. A future improvement could add a startup validation pass that warns on unrecognized provider names.

## Surprises

- `provider-interface.mts` compiled to `export {}` (empty JS) — TypeScript interfaces have no runtime representation. This is correct but easy to forget when checking the compiled output.
- `tsconfig.test.json` includes `src/**/*.mts` (not just `src/tests/`) due to `extends` from main tsconfig — tests can import from source directly without re-compilation. Clean but non-obvious.

## Followups

- SLICE-15: wire ceremony hooks (`start-slice.mjs`, `complete-slice.mjs`) to call `getProvider(config, repoPath)` instead of direct github-sync imports. That's when pluggability becomes live.
- Consider adding a `validateProviderConfig(config)` startup check that warns on unknown provider names — addresses the DEC-TBD consequence above.

## What went well

Clean 3-file + 1-test structure. TypeScript compilation caught zero issues on first build. Independent reviewer confirmed all 9 resolver paths without needing any back-and-forth. The back-compat alias (`github.enabled === true`) was straightforward to test and required no changes to existing configs.

## What went wrong

Nothing material. The only friction was discovering that `provider-interface.mts` emits an empty `.mjs` (because TypeScript interfaces strip at compile time) — briefly checked this wasn't a build error before proceeding.

## What I would do differently next time

For stubs like LinearProvider, consider marking the class with a `@stub` JSDoc tag and adding a lint rule or manifest check that prevents stub providers from being wired into production ceremony hooks. Right now the only guard is "provider=linear is misconfiguration" — making it structurally impossible would be stronger.
