## Lessons

- Marker-file pattern is a clean way to thread orchestration signals from CLI invocation into grade telemetry. Beats heuristics (counting reviewer artifacts to detect fanout) because it's explicit and unambiguous. Reusable pattern: `phase_gate_parallel`, `inline_path_used`, future levers.
- Dispatch-instruction text changes are PROMPT changes — they affect orchestrator behavior without touching upstream code. Within-repo wiring strategy works when orchestrator is parameterizable via string output. Pattern reusable for other ceremony-flow changes.
- Path-traversal CVE-class slipped past builder; Reviewer B caught it. Reinforces dual-reviewer ladder value — Reviewer A focused on correctness ACs, Reviewer B on production-readiness + security. Both lenses needed.

## Decisions

### DEC-051: Marker file signals fanout dispatch, not heuristic detection

**Rationale**: Counting reviewer artifacts to infer "fanout ran" is fragile — serial dispatch can produce 2 artifacts, fanout produces 2 reviewer artifacts + 1 validator. Lifetime-unique slice IDs + explicit marker is robust + auditable. The marker also lets future tooling distinguish "fanout dispatched but failed" from "fanout never invoked".

**Consequences**:
- positive: telemetry signal is explicit and deterministic
- positive: marker carries `taskCount` for future variant payloads (e.g. multidim 4-task fanout)
- negative: stale-marker risk if slice IDs were ever recycled (not current convention; not enforced by code)

## Surprises

- The dispatch-instruction text is consumed by `crew:lead` (upstream) AND parent loop (this repo). Same string drives both. Means a single-line wording change immediately affects ALL orchestration paths — no upstream coordination needed for the text itself.
- Builder used `safeSliceId(sliceId)` regex guard pattern matching the design's "use `path.basename()` or whitelist regex" — chose the more explicit regex variant. Good defensive choice.
