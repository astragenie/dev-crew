## Lessons

- Found and fixed a real production bug during implementation: `updateFeatureFrontmatter` cleared the listBacklog cache but NOT the frontmatter-cache. On Windows, where mtime granularity is ~16ms, rapid writes within the same tick share an mtime and the cache pinned the stale parse. This caused the slice-link test to fail intermittently and would have hit any in-process orchestrator (the SLICE-102 `slice close` command in particular). Fix is one extra `clearFrontmatterCache()` call.
- Refactor sliceFromFeature into two named branches (materializeSingleSlice + materializeProposedSlices) reads better than one switch — each branch has its own MaterializeOpts type and explicit return shape.
- Idempotent rerun for multi-slice uses `existingSlices.length >= proposed.length` — simple and correct, doesn't need to match titles or check filesystem. The feature's slices array is the source of truth.

## Surprises

- TypeScript union narrowing on the return shape forced a cast in one test (`out.slices[i] as { ..., points: number }`). The single-slice path returns objects without `points`; multi-slice returns objects with `points`. TS sees the union and refuses indexing on `points`. Acceptable in a test, but a future refactor could give the proposed-slice path a distinct return type or always include `points: number | undefined`.

## Followups

- Consider documenting the cache-invalidation contract: any writer that mutates a frontmatter-containing file must clear BOTH listBacklog AND frontmatter caches. Could be enforced via a single helper.
- Multi-slice path skips the architect classify step. Worth revisiting whether architect should classify each materialized sub-slice (proposed titles + bodies are author-supplied, but tags / needs_contract / needs_ux still need routing). Defer to a follow-up FEAT.

## What went well

- 5 new tests covering all paths: atomic multi-slice create (with effort_points round-trip), idempotent rerun, single-slice path unchanged (back-compat), malformed CLI exit + audit, undersized propagation.
- Discovery + fix of the mtime-cache bug came from running an existing regression test, not from new test design. The existing "is idempotent on the slice link" test was the canary.
- FEAT-168 closes cleanly across three sessions: SLICE-98 refuse-gate + audit, SLICE-99 parser arrays-of-mappings, SLICE-100 wire-up.

## What went wrong

- ~30 minutes spent diagnosing the cache bug. Debug scripts had to be written + deleted multiple times before the cache-coherency issue surfaced. The root cause was non-obvious (Windows mtime granularity).

## What I would do differently next time

- Test in-process orchestrators against the same fixture surface as multi-process CLI flows. The 3-step CLI never hit this bug because each subcommand starts a fresh process with empty caches. closeSlice would have hit it in production if it called sliceFromFeature internally — worth adding to the closeSlice regression suite.
