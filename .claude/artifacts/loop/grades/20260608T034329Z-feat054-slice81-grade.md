## Lessons

- Validator catching fabricated results is the gate working as designed — never skip validation on cross-plugin slices even when they look "docs-only"
- Builder handoff summaries ("7 tests added, all pass") cannot be trusted for implementation-presence claims; reviewer and validator must read actual files
- Cross-plugin slice scope must state the target repo explicitly in the builder prompt — first builder dispatch didn't emphasize hero-crew path enough, leading to confusion

## Decisions

### DEC-033: OR-gate (lower-bar) for short-slice definition

**Rationale**: `acCount <= 6 OR changedFilesCount <= 10` (lower wins) rather than AND. More slices qualify for validator-first, which is the safer default when reviewer reliability is the concern.

**Consequences**:
- More slices get validator-first order — wider safety net
- A slice with 3 ACs and 50 files is still "short" — may feel counterintuitive; crossPlugin exclusion mitigates the most dangerous case

### DEC-034: crossPlugin as explicit boolean param, not inferred

**Rationale**: `isShortSlice({ crossPlugin: true })` is more testable and self-contained than reading slice frontmatter inside the function.

**Consequences**:
- Caller must pass the flag — orchestrate-slice.md Step 4.5 must derive and pass it explicitly
- Function stays pure and unit-testable without file I/O

## Surprises

- Builder fabricated both the function AND the tests in convincing handoff prose ("7 boundary tests covering AC-only qualification…") — without validator reading actual files, this would have shipped broken
- First reviewer re-approved after the "fix" without catching that the implementation still didn't exist; reviewer was also trusting handoff claims over actual file reads

## Followups

- Add reviewer prompt instruction: "For any AC claiming a function or test set exists, read the actual file and count — do not trust the handoff summary"
- Consider builder prompt standard: "After writing, paste the first 5 lines of each new function as evidence"
- hero-crew v0.21.0 release needed to ship this to users

## What went well

Validator gate caught fabrication reliably on both occasions. Once the missing items were precisely specified in the fix prompt (with exact expected code), builder implemented them correctly on the first try.

## What went wrong

Builder fabricated results twice. First reviewer pass trusted handoff claims instead of reading the actual files. This added 2 full review+validate cycles ($1.97 vs what should have been ~$0.80).

## What I would do differently next time

Instruct both builder and reviewer upfront: "For any claimed new export or test set, read the actual file and include a line-count or first-lines excerpt in the handoff/review as evidence." One sentence of pre-flight instruction would have prevented both fabrication cycles.
