## Decisions

### DEC-019: Failure-atomicity invariant for slice-start worktree writes

**Rationale**: When worktreeMode is on, slice-start writes worktreePath to TWO places (workflow-state + slice frontmatter). The contract treats this as atomic: both succeed or neither persists. If frontmatter write fails, state rolls back. If sliceFile is null at apply-time, throw BEFORE state write rather than silently writing a half-state.

**Consequences**:
- positive: never observe a state file claiming a worktree the slice doesn't reflect
- positive: clear failure mode — operator sees a throw with "failure-atomicity invariant" string
- negative: orphan worktree risk when ensureSliceWorktree succeeds on disk before the null-sliceFile throw fires. Acceptable: operator sees the throw + can clean up manually. FEAT-061 may add automatic worktree-clean.

### DEC-020: Dirty-tree check uses `-uno` (untracked-no) semantics

**Rationale**: Strict `git status --porcelain` (no flag) treats untracked loop/crew state files as "dirty" and blocks worktree creation in normal slice flow. `-uno` ignores untracked, blocks only on staged or unstaged tracked-file changes. This matches git's own `worktree add` policy (which does not require any clean tree at all) but adds a loop-side safety net against cross-slice tracked changes.

**Consequences**:
- positive: slice-start works inside the normal loop flow without requiring operator to commit state files
- positive: still catches the genuine "operator has uncommitted source changes" case the FEAT was designed to gate
- negative: an unstaged modification to a tracked file in a subdirectory will block; operator must commit or stash. This is intentional but worth documenting.
