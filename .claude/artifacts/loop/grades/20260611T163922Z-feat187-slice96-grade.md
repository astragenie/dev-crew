SOP fallback (direct `crew:builder` dispatch) worked. Pattern persists beyond the 5-slice SOP threshold — upstream-request against hero-crew is justified.
- **Hard output contract works** — explicit "your LAST tool call MUST be Write/Edit/Bash; narration-only return is contract violation" in builder prompt produced a clean handoff artifact and 100% AC coverage on first dispatch.

## Decisions

### DEC-054: Kind registry is closed-set; new kinds require explicit registry update

**Rationale**: `KIND_REGISTRY` throws on unknown kinds rather than auto-registering. Forces a code review for every new artifact category. Open-set would let drift accumulate silently and defeat the unification goal.

**Consequences**:
- positive: new kinds land in registry + spec doc table simultaneously; no silent drift
- positive: tag-extraction stays deterministic — every kind maps to a documented semantic
- negative: writers in branches that add a new kind must touch both the writer and the registry; minor friction

### DEC-055: `camelTight` drops on overflow rather than truncating

**Rationale**: Truncated camelCase produces semantically broken tokens (`exposeCheckpointdueSliceClosesS`). Dropping the optional title segment keeps the canonical 4-tag shape (`ts-kind-feat-slice`) clean for memory-engine ingestion. Title belongs in frontmatter; the filename should not carry prose.

**Consequences**:
- positive: tag-extraction never produces garbage tokens
- positive: filenames stay short and uniform
- negative: long descriptive titles disappear from the filename surface — visible-in-dir-listing UX loses some context

## What went well

PM agent scoping pass caught the existing helper before SLICE-A started, shrinking effort from ~15 writer flips to 4 files. Hard-output-contract addendum on builder prompt produced a clean, exhaustive handoff with all 7 ACs covered first-pass. Parallel reviewer-A + reviewer-B + validator fanout cost ~5 minutes wall-clock vs ~15 minutes serial. Both reviewers correctly flagged the audit completeness gap without blocking the slice.

## What went wrong

`crew:lead` dispatched specialist-pause for the second time in two slices (SLICE-95, SLICE-96). Fell back to direct builder dispatch — works, but bypasses the orchestrator-mode policy and forfeits cost-attribution telemetry routed through lead. The audit doc shipped with one writer missing (`ceremonies.mts:122`), caught only by Reviewer B; suggests the builder's audit walk was based on grep heuristics that missed the `feature-end-` literal pattern.

## What I would do differently next time

- Add a deterministic-grep step to the builder prompt: "before writing the audit doc, run `grep -rn 'await fs.writeFile' src/scripts/lib/` and verify EVERY hit appears in your table". Trust the grep, not the walk.
- Pre-flight the lead with a 30-second test dispatch ("respond with `[MODE] team-run`") to catch specialist-pause before committing to a full slice ceremony. Cost <$0.10; saves ~5 min when lead pauses.
- File the upstream-request against hero-crew at the same time as the next specialist-pause observation, not after the third recurrence.
