## Lessons

- Marker + dispatch-instruction wiring pattern proven across 2 slices (SLICE-93 fanout, SLICE-94 shape). Reusable for any future ceremony signal: define marker schema → write at CLI invoke OR slice-start → read at grade-write → populate frontmatter. Symmetric across signal types.
- Extract-shared-helper-on-second-use rule worked: `slice-id-guard.mts` extracted from `fanout-marker.mts` on the second consumer. Avoided premature abstraction (would have been wasted if shape-marker hadn't shipped).
- Reviewer + validator false-positives on format gate happened simultaneously. Both ran `bun run format:check` and reported failure, but real run is clean. Could be stale state during transient builder iteration — worth investigating if recurring.

## Decisions

### DEC-052: Shared sliceId guard module — symmetric across all marker types

**Rationale**: SLICE-93's `fanout-marker.mts` introduced `SLICE_ID_RE` inline. SLICE-94's `shape-marker.mts` needs the same guard. Extract to `slice-id-guard.mts` so future markers (e.g., phase-gate-parallel signal if added) reuse it. Single regex definition prevents drift.

**Consequences**:
- positive: future markers automatically inherit traversal guard
- positive: regex update propagates to all consumers via single edit
- negative: one more import per marker file (minor)
