## Lessons

- `"text".includes("")` is always true in JavaScript — any glob overlap check using `includes` must guard against empty-string inputs or it becomes a match-everything backdoor. Trivial guard, non-trivial correctness impact.
- When adding a new template token (`{{rulesBlock}}`), always verify the token is returned from `buildTokens` in the same commit — template and wiring must be atomic or the token renders literally in output.
- A mid-slice context compaction forces review-round re-derives. Checkpoint state to a handoff artifact before the context window fills to prevent this overhead.

## Decisions

### DEC-042: Guard empty-string patterns in patternSubsumed rather than allowlist

**Rationale**: `patternSubsumed` used `p1.includes(p2)` for overlap detection. `String.includes("")` returns true for any input so a rule with `globs: [""]` would match every inScopeGlob. Added `if (!p1 || !p2) return false` guard as the minimal fix rather than switching to an explicit allowlist. Guard is the correct semantic: empty patterns should not subsume anything.

**Consequences**:
- Rules with empty-string globs are now correctly filtered out (non-matching)
- `alwaysApply: true` remains the correct opt-in for unconditional rules
- No behavior change for well-formed glob patterns

### DEC-043: rulesBlock wiring added to buildTokens extras interface

**Rationale**: Template `{{rulesBlock}}` token was added but `buildTokens` did not return it, causing `renderTemplate` to leave the literal `{{rulesBlock}}` in rendered output. Fixed by extending the `extras` parameter with `rulesBlock?: string` and returning it (defaulting to `""`). Alternative of a separate token builder was rejected — `buildTokens` is the canonical token assembly point.

**Consequences**:
- `{{rulesBlock}}` token is now properly substituted in rendered templates
- Callers must pass `rulesBlock` via `extras` to populate it (wiring from `loadRules` → `buildRulesBlock` → `buildTokens` is a follow-up task)
- Pattern established: all template tokens must be threaded through `buildTokens` extras

## Surprises

- The empty-string glob bug was introduced by a well-intentioned substring overlap heuristic. The fix is a one-liner but the bug would have been invisible until a rule file with an empty `globs:` entry was deployed.
- AC-8 test count check failed post-builder: we had 1087 before the session started but AC-8 counted from an earlier baseline. The gap was only noticed during review, not at builder self-verify.

## Followups

- Wire `rulesDir` into `loop.json` config schema and call `loadRules(rulesDir)` + `buildRulesBlock(rules, inScopeGlobs)` from the install flow (FEAT-082 follow-up slice or FEAT-083+)
- Consider replacing heuristic glob overlap with `minimatch`/`picomatch` for exact pattern semantics
- Add observability: log (at debug level) which rules matched and why when `buildRulesBlock` runs

## What went well

loadRules and buildRulesBlock were well-scoped and implemented cleanly in the builder pass. The helper extraction to stay under the cyclomatic complexity cap (15) worked well. Both reviewers caught real bugs that would have shipped silently — the review gate did its job. The validator confirmed all 5 behavioral scenarios in one pass.

## What went wrong

Two critical bugs escaped the builder's self-verify: empty-string glob false positive and missing `rulesBlock` in `buildTokens` return dict. The first review round failed because the builder did not test edge cases (empty globs, empty body) as explicitly requested in the AC. Context window compaction mid-session added overhead and required re-deriving state.

## What I would do differently next time

Add a self-verify checklist step before submitting to review: explicitly test the empty/null/undefined cases for every new function. For template tokens, always grep for all `{{token}}` references in the template file and verify each one is in `buildTokens` before claiming the builder pass is done.
