## Lessons

- SubagentStop hook fires on orchestrator-returns-to-user, not on subagent-finish. Any code reading `events.jsonl` immediately after a dispatch (slice-complete, telemetry roll-ups) cannot rely on stop events being present yet. Design for partial windows.
- 58% of historical agent reports (18 of 31) had been silently zero. The diagnostic note now makes the partial-window case visible to the reader instead of looking like "nothing happened during the slice."
- Test helper that always wrote a `subagent_stop` event hid the failure mode for months. Fixture flexibility (here: `stopTs: null` skips the stop event) is what made the bug testable.

## Decisions

### DEC-006: Pair agent events by union of start+stop ids, not by stop ids alone

**Rationale**: `subagent_stop` events lag behind their corresponding starts because the SubagentStop hook fires when the orchestrator returns control to the user — that can land minutes after `/loop:slice complete` runs. Counting agents only when their stop event was visible meant the writer collapsed to `agent_count: 0` for any slice whose builder dispatch was the last action before the close ceremony. Pairing on the union of agent_ids restores correctness without waiting for the stop, and the diagnostic note makes the partial-data case explicit to readers.

**Consequences**:
- positive: agent_count is now load-bearing again; observability for builder-turn cost is restored across the marathon loop.
- positive: writer is robust to any future hook-lag, not just this specific symptom.
- negative: in-flight agents contribute zero turns and zero duration (no transcript path on start payload). Could be addressed by a follow-up pass that re-reads events.jsonl when the stop finally lands.

## Surprises

- Diagnosis took longer than the fix. Initial hypothesis was "stop-hook regression" — turned out to be hook lifecycle by design.
- Real-data probe on SLICE-27 yielded 3 agents, not 1 as expected from the in-flight case alone. Two of them had `subagent_stop` payloads with null `agent_type` (existing path through `buildAgentPair`) — orthogonal data-quality issue surfaced as a side effect.

## Followups

- Optional slice: re-read events.jsonl after a delay (or on next slice start) and rewrite reports that previously had in-flight agents. Would let turn counts catch up.
- Investigate the "unknown" agent_type rows in the SLICE-27 probe — stop payloads loading with null `agent_type` suggests payload normalization needs review.

## What went well

Pivot from "log FEAT and defer" to "fix now" was clean because SLICE-27 had just been pushed. Tree was clean enough to do surgical commit limited to SLICE-28 scope (skipped the CLAUDE.md / docwriter test drift that landed from elsewhere).

The diagnostic note in the report body is the highest-leverage observability change in this slice. Future readers will see "1 agent(s) have no `subagent_stop` event recorded" instead of "No agents were dispatched during this slice" and trust the report.

## What went wrong

Initial AC-4 was framed as "diagnose hook regression" — but there was no regression. The asks should have been framed as "characterise the timing" from the start, not "find the bug in the hook."

Test helper `writeAgentEvents` needed a small contract change (`stopTs: null` → skip stop) to model the in-flight case. Easy in hindsight but easy to miss when only the happy path is tested.

## What I would do differently next time

Start by sampling the actual events stream on disk before forming hypotheses about hook regressions. The events.jsonl tail in the first ten minutes would have shown that stops arrive in batches, eliminating the regression hypothesis early.
